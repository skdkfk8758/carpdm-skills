# UI 인수 검증 — 시안 갭 분석 + 인터랙션 실구동 (공유 SSOT)

IMPORTANT: 이 파일은 **구현이 끝난 UI 를 사람이 쓰듯 실제로 눌러 확인하고, 승인 시안과의
갭을 표로 못 박는** 절차의 단일 SSOT 다. 소비자: `pipeline.md` Phase 4(forge / hunt /
renew) · `orchestrated.md` §4 Stage B · `linear-goal` Phase 3 Goal Prompt. **복제 금지 —
소비자는 이 파일을 읽어 따르고, 절차를 자기 파일에 재기술하지 않는다.**

존재 이유: 테스트 수트 green 은 *코드가 스스로에 대해* 맞다는 신호이고, 렌더 스크린샷은
*그려진다*는 신호다. 둘 다 **"submit 버튼을 눌렀을 때 실제로 저장되는가"** 를 말해주지
않는다. 시안 대조도 스크린샷 한 장으론 정적 초기 상태만 본다 — hover/focus/error/loading
상태는 눌러봐야 나온다. 이 두 구멍(동작 미검증 · 상태 미대조)이 "테스트 다 통과했는데
버튼이 안 먹는다"의 구조적 원인이다.

## 0. 적용 판정 (먼저)

**돈다** — 이번 변경이 사용자 대면 UI 표면을 추가·수정했고, 그 표면에 **인터랙티브 요소가
1개 이상**(버튼 · form · input · select · 링크 네비게이션 · 토글 · 모달 트리거) 있을 때.
시안(승인 mockup) 유무와 무관 — 시안이 없으면 Part C(갭 분석)만 생략하고 Part A/B 는 돈다.

**안 돈다** — 순수 백엔드/API/DB/CLI/라이브러리 변경, 인터랙티브 요소가 0인 정적 표시
변경(카피 문구 한 줄 · 색상 토큰 교체). 이때는 pipeline 의 기존 런타임 스모크로 충분하며
Part A~C 와 §4 게이트를 돌지 않는다.

**단 §5·§5.1 은 표면과 무관하게 적용된다.** 비UI 변경이어도 `[사용자 직접 확인 필요]` 가
남으면 §5(2건+ → 체크리스트 아티팩트)·§5.1(1건+ → dev 서버 인계)만 읽어 인계한다 — 앞
Part A~C 는 여전히 건너뛴다. *확인을 사람에게 넘기는 일*에 UI 여부는 상관이 없다: 항목이
"[저장] 을 눌러 토스트 확인" 대신 "`curl -s localhost:8080/api/x` → 200 + `{"ok":true}`
확인"이 될 뿐이고, 흩어진 채로 두면 놓치는 것도 똑같다.

**부분 적용** — 변경이 UI+백엔드 혼합이면 UI 표면에만 적용한다. **이번 diff 가 만든/바꾼
요소만** 대상이다 — 기존 화면 전수 회귀는 이 게이트의 일이 아니다(범위 폭발).

## 1. Part A — 인터랙션 인벤토리 (구동 전, 필수)

구동 대상을 **diff 에서 기계적으로 뽑아** 목록화한다. 목록 없이 눌러보면 "눌러본 것만
검증됨"이 되고 빠진 게 안 보인다.

diff 의 추가·수정 파일에서 아래를 Grep/Read 로 수집:

- `<button>` · `<a href>` · `onClick` / `onPress` / `@click` 핸들러
- `<form>` · `onSubmit` · `<input>` / `<select>` / `<textarea>` / `<input type=checkbox|radio>`
- 라우팅 트리거(`navigate(` · `router.push` · `<Link>`)
- 모달/드로어/토스트 오프너, 토글·탭 전환
- **plan Acceptance 장부의 `[AGENT]` 항목** (2026-07-30) — diff 추출 요소와
  합집합으로 인벤토리에 합류시킨다. UI 성 항목은 아래 Part B 로 실구동, 비UI 성
  항목(`curl`/CLI)은 인벤토리에 두되 브라우저 대신 해당 명령 실행+실제 출력으로
  판정한다. Acceptance 가 이 게이트 밖에서 사람 몫으로 새는 것을 여기서 막는다.

각 항목을 한 줄로 적는다 — **`요소 · 기대 동작 · 관찰 가능한 성공 신호`**:

```
1. [저장] 버튼 · 폼 제출 → POST /api/x 200 + 성공 토스트
2. email input · 빈값 submit → 인라인 에러 "이메일을 입력하세요"
3. [취소] 버튼 · 모달 닫힘 + 입력값 초기화
```

**성공 신호는 관찰 가능해야 한다** — "동작함" 금지. DOM 변화 · 네트워크 요청 · URL 변화 ·
콘솔 무에러 중 최소 하나로 진술한다(karpathy 원칙 4).

인벤토리가 **비면** 적용 판정이 틀린 것이다 — §0 으로 돌아가 비적용 처리하고 그 사실을
기록한다.

## 2. Part B — 실구동 (chrome MCP)

dev 서버(또는 정적 빌드)를 띄우고 브라우저에서 인벤토리를 하나씩 **실제로 조작**한다.
도구는 `mcp__claude-in-chrome__*` — 이름은 아래가 정확한 것들이다(추측 금지):

| 목적 | 도구 |
|---|---|
| 탭 확보 | `tabs_context_mcp` → `tabs_create_mcp` (기존 탭 재사용 금지 — 사용자가 명시 요청할 때만) |
| 이동 | `navigate` |
| 요소 찾기(ref 획득) | `find`(자연어) 또는 `read_page` |
| 클릭·타이핑·스크린샷 | `computer` (`action: left_click` / `type` / `screenshot` / `hover` — **`take_screenshot` 이란 도구는 없다**) |
| form 값 세팅 | `form_input` (ref + value — select/checkbox 는 이쪽이 확실) |
| 결과 관찰 | `read_page`(DOM 변화) · `read_console_messages`(`onlyErrors:true`) · `read_network_requests`(`urlPattern` 으로 이번 API 만) |

절차 (항목당):

1. **before 관찰** — 필요하면 `computer screenshot` 또는 `read_page` 로 조작 전 상태 확보.
2. **조작** — 클릭/입력. 좌표 클릭보다 `find`/`read_page` 의 `ref` 를 쓴다(좌표는 렌더 흔들림에 취약).
3. **after 관찰** — 인벤토리에 적은 *그 성공 신호*를 확인한다. DOM 이면 `read_page`,
   API 면 `read_network_requests` 로 요청 URL+상태코드, 에러면 `read_console_messages`.
4. **판정 기록** — `pass` / `fail(관찰된 실제 결과)` / `blocked(사유)`.

**추가 필수 관찰 — 상태 축.** 인벤토리를 다 돌린 뒤 최소 이 셋은 유발해서 본다(해당하면):

- **에러 상태** — form 이 있으면 잘못된/빈 입력으로 1회 submit → 검증 메시지가 뜨는가.
- **로딩/비활성 상태** — 비동기 액션이 있으면 진행 중 disabled/스피너가 있는가(없으면 중복 제출 가능 → 발견).
- **콘솔** — 전 구동 끝나고 `read_console_messages({onlyErrors:true})` 1회. 새 에러 = fail.

### 안전 (비협상 + 2026-07-30 재정의 — "파괴적"의 경계를 정확히)

- **dev/로컬 환경만.** prod URL 구동 금지. 쓰기 경로는 dev 데이터로만.
- **절대 금지 (dev 여도)** — **경계 밖 발신**: 메일·SMS·웹훅·실결제·외부 API 쓰기
  (dev 에서도 진짜 나간다), prod 데이터를 건드리는 조작, 복구 경로 없는 조작.
  인벤토리에 있으면 `blocked(외부 발신 — 수동 확인 이관)` 으로 §V 이관.
- **허용 (조건부 — 종전 blanket ban 완화)** — 삭제·상태변경 컨트롤이라도
  **dev/로컬 AND 대상이 시드/테스트 데이터 AND 복원 경로 확인**(재시드 스크립트·
  재생성 가능·트랜잭션 롤백)이면 **실구동한다** — dev 시드 row 의 "삭제 버튼"은
  파괴적이지 않다. 판정 증거(왜 dev 데이터이고 어떻게 복원되는지) 1구절을 기록에
  남긴다. 복원 경로를 확인 못 하면 종전대로 `blocked` 이관 — 허용은 증거 있는
  경우만(기본 동작 불변).
- **JS `confirm`/`alert` 는 유발 전 오버라이드** — 브라우저 네이티브 모달이 뜨면
  이후 도구 호출이 전부 막힌다. dialog 를 띄우는 컨트롤을 (위 규칙상 구동 가능하면)
  누르기 **전에** `javascript_tool` 로 `window.confirm = () => true; window.alert =
  () => {};` 를 주입하고 클릭한다 — 주입 사실을 판정 기록에 남긴다. 주입이 안 먹는
  네이티브 다이얼로그(`beforeunload`·브라우저 권한 프롬프트)만 종전대로 `blocked`
  이관.

### 폴백 사다리

브라우저 도구가 **2회 연속 실패**하면 재시도를 멈추고 내려간다 — 절차 SSOT 는
`~/.claude/rules-ondemand/browser-verify-fallback.md`(복제 금지). 요지: Chrome bridge 실패
→ Playwright → curl/API 직접 → 테스트·diff ground-truth. **내려갔으면 그 사실을 결과에
명시**하고, 시각/인터랙션 확인이 대체 불가한 항목은 green 으로 위장하지 말고 §V
`[사용자 직접 확인 필요]` 로 남긴다.

## 3. Part C — 시안 갭 분석 (승인 시안이 있을 때만)

승인 mockup(`deep-plan` companion `.html` · `mockup` 산출 시안 · 사용자가 준 시안)이
있으면, Part B 에서 띄운 **그 렌더를 재사용**해(이중 구동 불요) 시안과 대조한다. 대조는
스크린샷 vs 시안 **양쪽을 실제로 보고** 판정한다 — 코드만 읽는 대조는 폴백이다.

**초기 화면 한 장으로 끝내지 않는다.** 시안이 상태별 화면(에러 · 로딩 · 빈 상태 · hover)을
담고 있으면 Part B 에서 그 상태를 유발한 시점의 스크린샷으로 각각 대조한다 — 정적 대조가
놓치는 구멍이 여기다.

### 4축 + 갭 표

| 축 | 본다 |
|---|---|
| **구조** | 요소 유무·계층·순서. 시안에 있는데 구현에 없음/추가됨 |
| **레이아웃** | 정렬·간격·크기 비율·반응형 브레이크 거동 |
| **스타일** | 색·타이포·radius·shadow — 프로젝트 토큰 기준(raw hex 하드코딩은 그 자체가 갭) |
| **상태·전이** | hover/focus/disabled/error/loading/empty 가 시안대로 존재하는가 |

발견을 표 하나로 못 박는다(산문 금지 — 후속 처리 단위가 행이다):

```
| # | 축 | 시안 | 구현 | 판정 | 처리 |
|---|-----|------|------|------|------|
| 1 | 구조 | 우측 필터 패널 | 없음 | gap | Phase 3 loop-back |
| 2 | 스타일 | --color-accent | #3b82f6 하드코딩 | gap | Phase 3 loop-back |
| 3 | 레이아웃 | 카드 간격 24px | 20px | 수용 | 잔여 리스크(사용자 합의) |
```

**판정 3분류** (pipeline 의 intent 판정과 같은 어휘):

- **gap** — 시안과의 객관적 불일치 → **confirmed gap**, Phase 3 로 돌아가 그 delta 만 짓는다.
- **out of scope** — 시안이 이번 범위 밖까지 그린 것 → 이유 적고 기각.
- **plan defect** — 구현이 맞고 *시안*이 틀림 → 시안을 amend(같은 파일 경로로 재-publish).

**미감·질감 판단**(폰트 무드, 카피 톤, "좀 답답해 보임")은 gap 이 아니라 `[HUMAN]` 항목이다
— 사용자와 walk 해 합의한다. 객관적 불일치만 게이트로 친다.

## 4. 게이트 (hard)

**출시 조건: 인벤토리 전 항목이 `pass` 이거나 명시 처리됐고 AND 갭 표에 미처리 `gap` 이
없고 AND §5 트리거가 걸렸으면 체크리스트 아티팩트가 실제로 publish 됐을 것 AND §5.1
트리거(사람 몫 확인 1건+)가 걸렸으면 실측 dev origin 이 보고에 실렸을 것**(서버가 없는
프로젝트면 §5.1-0 대로 그 사실이 적혔을 것).

세 번째 절은 §5 를 게이트 안으로 끌어온 것이다 — 조건절이 아니라 **통과 요건**이다.
실측(ADT-406, 2026-07-25): 이 파일을 §5 까지 다 읽고 Part A~C·게이트를 완주한 실행이
§5 만 조용히 건너뛰었다. §5 가 게이트 밖의 권고 문단이라 빠져도 아무 신호가 없었기
때문이다. 트리거가 걸렸는데 아티팩트가 없으면 **이 게이트는 통과하지 않은 것**이며,
종료 보고에 URL 이 없는 것 자체가 미완의 표식이다.

- `fail` 1건 = confirmed gap → **Phase 3 loop-back**(그 항목만 TDD 로 고치고 Phase 4 재진입).
  green 으로 넘기지 않는다.
- `blocked`(파괴적 컨트롤 · 브라우저 불가 · env 부재) = 출시를 막지 않지만 **반드시** §V
  `[사용자 직접 확인 필요]` 로 이관한다 — 확인 방법 1구절과 함께. 조용히 사라지는 것이
  이 게이트의 유일한 실패 모드다.
- **인벤토리를 안 만들고 "몇 개 눌러봤음"으로 통과 선언 금지.** 인벤토리가 장부다.

### 증거 배출

이 게이트의 산출은 소비자의 종료 출력으로 흘러간다(`output-contract.md`):

- 구동해서 `pass` 한 항목 → §V `[직접 테스트 완료]` (조작 → 관찰된 실제 결과를 증거로).
- `blocked` 항목 → §V `[사용자 직접 확인 필요]` (체크박스 + 확인 방법).
- 갭 표의 `수용` 행 → 잔여 리스크로 §R 보드 평결에.

증거는 **관찰된 실제 출력**이어야 한다 — "버튼 정상" 금지, "저장 클릭 → POST /api/x 201,
토스트 노출 확인" 처럼(`~/.claude/rules/verification-safety.md` V1).

### 5. 인터랙티브 체크리스트 아티팩트 (`[사용자 직접 확인 필요]` 2건+ 일 때)

`[사용자 직접 확인 필요]` 항목이 **2건 이상** 남으면 — 터미널의 §V 텍스트 체크박스에 더해
— 사람이 살아 있는 dev 서버를 보며(UI 면 눌러, API·CLI 면 때려) 채우는 **인터랙티브
체크리스트를 Artifact 로 publish** 한다.
백그라운드 잡(walk 불가로 전 항목이 `[사용자 직접 확인 필요]`)·다이슈 묶음(linear-goal /
land 꼬리)에서 특히 그렇다 — 흩어진 수동 확인 항목을 사람이 놓치지 않게 한 화면에 모은다.

- **트리거**: `[사용자 직접 확인 필요]`(=미검증 `[HUMAN]`·`blocked`) **2건+**. **표면 무관** —
  UI 든 API·CLI·배치든 사람 몫 확인이 2건 이상 흩어지면 모은다(§0 의 §5 예외).
  1건이면 §V 텍스트 한 줄로 충분 — 아티팩트는 과함(karpathy 원칙 2). 단 **서버 인계(§5.1)는
  1건부터** — 확인할 화면·엔드포인트가 죽어 있으면 한 건도 못 채운다.
- **재료**: `~/.claude/skills/craft-core/references/assets/human-checklist-template.html` 를
  복사해 치환한다(파일 상단 주석이 치환 규칙 SSOT — self-contained·테마대응·localStorage
  저장·진행률이 이미 들어있다, 새로 디자인하지 말 것). 항목 = **§V `[사용자 직접 확인 필요]`
  블록 그대로**(이미 `pass` 한 `[직접 테스트 완료]` 는 제외 — 사람이 다시 누를 필요 없음).
  UI 경로면 그 소스가 Part A 인벤토리의 `blocked` + 미검증 `[HUMAN]` 이고, 비UI 경로면
  Acceptance 장부의 미검증 `[HUMAN]` + 스모크 skip 이관분이다. 각 항목은 관찰 가능한 성공
  신호로(§4 증거 규율 그대로) — 비UI 면 실행할 명령과 기대 출력을 그대로 적는다.
- **서버 선행 기동 (필수)** — 아래 §5.1. 체크리스트는 *사람이 눌러 볼 화면·때릴 엔드포인트*
  를 전제하므로, 띄워두지 않으면 첫 항목에서 막힌다.
- **publish**: `Artifact` 도구(파일 경로 + favicon). publish 전 `artifact-design` 스킬을
  로드하는 계약은 유지되나, 이 템플릿은 이미 그 기준을 만족하므로 **재디자인이 아니라
  치환·검수**만 한다. 링크 origin 은 §5.1 이 **실측한 값만** 쓴다(추정 금지).
- **보고 연결**: §V 블록 아래(또는 §N `열기` 행)에 아티팩트 URL 을 건다 — 텍스트 체크박스와
  아티팩트는 같은 항목의 두 표면이므로 항목을 **양쪽에 이중 나열하지 않는다**(터미널은 요약,
  아티팩트가 상세·조작면). 전 항목 체크 시 남는 후속(이슈 Done 전이·wt-sweep)은 아티팩트
  하단 노트에 안내한다.
- **결과 회수**: 템플릿의 **"결과 복사" 버튼**(빌트인)이 체크 상태를 Linear 코멘트 형
  markdown(`## 사용자 직접 확인 결과 N/M` + `### [ID] 섹션` + `- [x]/- [ ]`)으로 복사한다.
  사용자가 이것을 **세션에 붙여넣으면** agent 는 `- [x]` 항목을 §V 장부의 검증 완료로
  반영하고(대응 AC 체크·Linear 코멘트 갱신 — `acceptance-criteria-gate` G3), `- [ ]` 항목은
  잔여로 유지한다. localStorage 는 그 브라우저에만 남으므로 이 붙여넣기가 유일한 회수
  경로다 — 보고·NOTES 에서 이 경로를 한 줄로 안내할 것(전 항목 체크 시 완료 배너가
  같은 안내를 자동 표시한다).
- **한계**: 아티팩트는 사람이 채운다 — agent 가 그 체크를 대신 켜서 "검증됨"으로 만들지
  않는다(false-green, `acceptance-criteria-gate` G2). **붙여넣은 `- [x]` 도 사람의 자가보고다**
  — 보안 불변식 항목은 이것만으로 닫지 않는다(G4 직교 게이트 유지). agent 가 브라우저로
  직접 walk 가능하면 그건 `[직접 테스트 완료]` 경로지 이 아티팩트가 아니다.

### 5.1 dev 서버를 띄운 채 넘긴다 (사람 몫 확인이 **1건이라도** 남으면)

체크리스트만 주고 서버를 내리면 사람은 링크를 눌러 `ECONNREFUSED` 를 만난다. `[사용자 직접
확인 필요]` 가 **1건이라도** 남으면 — 아티팩트(§5) 를 내든 §V 텍스트 한 줄로 끝내든 —
**작업한 브랜치/워크트리의 dev 서버를 살려둔 채** 넘긴다. 아티팩트 없이 1건일 때는 그
origin 을 §V 항목의 "확인 방법" 구절에 박는다(`http://localhost:3010/settings 에서 …`).
확인 표면을 죽여둔 채 "확인해 주세요"는 확인을 요청한 게 아니다.

0. **기동 가능한지 먼저 본다** — `devserverctl.py` 가 dev 명령을 auto-detect 한다
   (Makefile 의 `dev:` 타깃 → 없으면 package.json 의 `dev` 스크립트). 둘 다 없으면 이
   프로젝트엔 띄울 서버가 없는 것(순수 라이브러리·CLI·배치) → **기동을 생략하고**, §V 항목의
   확인 방법을 서버 없이 실행 가능한 형태(테스트 명령·CLI 호출·로그 경로)로 적는다.
   억지로 띄우려 `--cmd` 를 지어내지 말 것.
0.5 **포트 중복부터 확인한다** — `:3000` 은 대개 이미 다른 프로젝트(또는 **메인 체크아웃의
   다른 브랜치**)가 물고 있다. 그런데도 기동은 성공한다 — Next/Vite 는 조용히 다음 빈 포트로
   옮겨가기 때문이다. 그래서 충돌은 실패가 아니라 *잘못된 URL* 로 나타난다.

   ```bash
   python3 ~/.claude/skills/dev-server-daemon/scripts/devserverctl.py ports --port 3000
   #  → ":3000 TAKEN by pid 21264 (node)  → free alternative: 3001"  또는 ":3000 free"
   ```

   물려 있으면 그 대안 포트를 1항의 `--port` 로 넘긴다(스크립트가 다시 한 번 검사하고,
   막혀 있으면 기동 자체를 거부한다). Vite 는 `PORT` 를 안 읽으므로 그때만
   `--cmd "npm run dev -- --port <빈포트>"`.

1. **daemon 으로 띄운다** — `run_in_background` 나 `&`/`nohup` 은 턴 종료 시 tree-kill 로
   죽어 체크리스트가 도착하는 순간 이미 서버가 없다. `dev-server-daemon` 의 스크립트가
   double-fork 로 세션 밖에 재부모화한다:

   ```bash
   python3 ~/.claude/skills/dev-server-daemon/scripts/devserverctl.py start \
     --cwd <작업 워크트리 절대경로> --name <워크트리 구분 이름> --port <0.5 에서 확인한 빈 포트>
   ```

   **`--cwd` 는 반드시 이번에 바꾼 코드가 있는 워크트리**다 — 메인 체크아웃(다른 브랜치)을
   가리키면 사람은 *변경이 없는 화면*을 보며 체크하게 된다. `--name` 도 워크트리마다 다르게
   준다(기본값이 cwd basename 이라 같은 레포의 두 워크트리가 한 이름으로 겹친다 — 겹치면
   `start` 가 "already running" 으로 **남의 워크트리 서버**를 그대로 보고한다. 이 경우
   스크립트가 기록된 `cwd` 와 CWD MISMATCH 경고를 함께 찍으므로, 그 경고가 보이면 URL 을
   쓰지 말고 다른 `--name` 으로 다시 띄운다).
2. **origin 을 실측한다** — 스크립트가 찍은 URL·포트를 그대로 쓴다. 관례값(`:3000`)을
   가정하지 않는다. 보고되는 포트는 **이 daemon 의 프로세스 그룹이 소유한 것만**이라, 거기
   실린 포트는 이번 서버의 것이 맞다. 반대로 "owns NO listening port" 가 나오면 아직
   컴파일 중이거나 실패한 것 — 빈칸을 관례값으로 메우지 말고 `logs` 로 확인하고, 그래도
   안 되면 3항으로. `!! :NNNN appears in this server's log but is owned by pid …` 경고가
   찍히면 그 URL 은 **남의 서버**다(프레임워크가 포트를 옮겼는데 배너는 원래 값을 찍은 경우) —
   절대 인계면에 넣지 않는다.
3. **그 origin 을 인계면에 박는다** — 아티팩트를 낼 때는 `{{DEV_ORIGIN}}`·route 링크·foot,
   안 낼 때(1건)는 §V 그 항목의 확인 방법 구절. 서버가 끝내 안 뜨면 **링크를 만들지 않고**
   라우트/엔드포인트 경로만 텍스트로 두고, 아티팩트의 `{{SERVER}}` 블록(또는 §V 항목 옆)에
   기동 명령과 실패 사유를 적는다(죽은 링크가 붙은 체크리스트가 제일 나쁘다).
4. **넘길 때 알린다** — 종료 보고에 origin + 정지 명령(`… stop --cwd <경로>`)을 한 줄로.
   daemon 은 세션이 끝나도 살아 있으므로 **끝났다고 스스로 내리지 않는다** — 사람이 체크를
   다 채운 뒤 내리는 게 정상 수명이다.

실측 근거(ADT-406): 워크트리 서버를 `:3010` 에 띄워 검증한 뒤 정리하며 내려버리고,
아티팩트에는 관례값 `:3000`(= 메인 체크아웃, **다른 브랜치**)을 박았다 — 링크는 살아
있는데 그 화면엔 이번 변경이 없는, 가장 탐지하기 어려운 형태의 죽은 링크였다.

같은 오류를 스크립트도 만들 수 있었다(2026-07-29 수정): `start` 가 포트를 **머신 전역
스냅샷**으로 보고해, 다른 프로젝트의 `:3000` 이 이번 서버의 URL 로 섞여 나왔다. 지금은
프로세스 그룹 소유 포트만 보고한다 — 위 0.5/2 항이 그 위에 서 있다.

## Anti-patterns

- 스크린샷 한 장 찍고 "시안대로 나옴" — 상태별 화면 미대조, 동작 미검증.
- 테스트 수트 green 을 인터랙션 검증으로 갈음 — 별개 신호다(수트는 코드↔코드).
- 인벤토리 없이 눈에 띄는 버튼 몇 개만 클릭 — 빠진 게 안 보임.
- 브라우저 도구 3회+ 재시도 — 2회 캡 위반(fallback 룰).
- 외부 발신(메일·결제·웹훅) 버튼을 "검증이니까" 클릭 — 절대 금지, 수동 이관.
- 반대 방향도 anti-pattern: dev 시드 데이터의 삭제 버튼을 복원 경로 확인 없이
  일괄 `blocked` 이관 — 안전 절의 허용 조건을 판정하지 않은 게으른 이관은 사람
  확인 인플레이션이다.
- `blocked` 를 보고에서 누락 — 미검증이 검증됨으로 위장.
- 이번 diff 밖 기존 화면까지 전수 구동 — 범위 폭발, 이 게이트의 일 아님.
- 체크리스트 아티팩트의 항목을 agent 가 대신 체크 — 사람이 채우는 면이다(§5, false-green 금지).
- `[사용자 직접 확인 필요]` 2건+ 인데 흩어진 텍스트 체크박스로만 남김 — §5 아티팩트로 모은다.
- 확인 항목을 남기면서 dev 서버는 내린 채 인계 — 1건이어도 §5.1. 사람은 첫 항목에서 막힌다.
- 포트 중복확인 없이 띄우고 `:3000` 을 인계 — 기동이 성공해도 프레임워크가 포트를 옮겼을 수
  있다(§5.1-0.5). 살아 있는 남의 화면이 제일 탐지하기 어렵다.
- 같은 `--name` 으로 다른 워크트리에 `start` → "already running" 을 그 워크트리 서버로 오인
  (§5.1-1 CWD MISMATCH 경고를 무시).
- 비UI 변경이라 §0 비적용이라며 §5·§5.1 까지 건너뜀 — *인계*는 표면 무관(§0 예외). 건너뛰는 건 Part A~C·§4 게이트뿐.
- 띄울 dev 명령이 없는 프로젝트(라이브러리·CLI)에 `--cmd` 를 지어내 기동 — §5.1-0 대로 생략하고 서버 없는 확인 방법을 적는다.
