# Design Context — 시안이 실구현을 닮게 만드는 공유 계약

이 파일은 **시안 충실도의 SSOT** 다. `mockup` 스킬이 직접 쓰고, `deep-plan`(Step 3)·
`craft-core` pipeline(Phase 1 companion)·`deep-prompt`(§3.5) 가 UI 시안을 만들 때
로드한다. 여기 규칙을 소비처에 복제하지 말 것 — 개정은 이 파일 한 곳에서 한다.

왜 존재하나: 시안이 프로젝트의 디자인 실체를 읽지 않고 즉흥 창작되면 구현과
괴리된다(실측: AUT-60 brands-menu 시안 vs 구현, Intelligence 작업 다수). 시안은
"예쁜 그림"이 아니라 **구현 후 모습의 예고**다 — 예고가 틀리면 리뷰 합의가 무효가
되고, 빌드 단계의 시안충실도 게이트가 잘못된 타겟을 강제한다.

## 목차

- 1. Design context 추출 — 시안 작성 전 7항목
- 2. DESIGN.md 해석 — 인라인형 vs 포인터형
- 3. DESIGN.md 부재 폴백
- 4. 4축 충실 계약
- 5. 검증 — 기계(토큰 체크) + 사람(실화면 대조)
- 6. net-new UI — 전문 스킬 위임 시 계약 주입

## 1. Design context 추출 — 시안 작성 전 7항목

시안 HTML 을 한 줄이라도 쓰기 전에, 대상 프로젝트에서 다음 7항목을 추출해
**context 블록으로 명시**한다(시안 보고에 포함). 항목이 없으면 비워두지 말고
"없음(사유)" 를 적는다 — 빈칸은 "안 찾아봄"과 구분이 안 된다.

| # | 항목 | 소스 (우선순위 순) |
|---|---|---|
| 1 | **토큰 값 집합** — 색·radius·font·spacing 실값 | DESIGN.md 인라인 표 → DESIGN.md 가 가리키는 코드(`theme.ts`·`globals.css @theme`·CSS var 블록) |
| 2 | **컴포넌트/class 어휘** — 재사용할 카드·테이블·뱃지·버튼·pill 등의 실존 class/구조 | DESIGN.md 카탈로그 → `globals.css` 헤더 주석 → 컴포넌트 디렉토리 |
| 3 | **미감 원칙·하드룰** — "raw hex 금지", "장식 아이콘 금지", 키컬러 단일 액센트 등 | DESIGN.md 명문 + `design-lint` 류 스크립트가 있으면 그 금지 패턴 |
| 4 | **대표 실화면 1~2개 경로** — 레이아웃 밀도·여백 감각의 기준점 | DESIGN.md 의 living reference 지목 → 시안 대상과 가장 비슷한 기존 페이지 파일 |
| 5 | **브레이크포인트** — 반응형 기준 | `globals.css` 등의 `@media` grep (0건이면 "없음 — 반응형 미정의") |
| 6 | **모션 규칙** — 애니메이션 어휘 | `@keyframes` grep + DESIGN.md 모션 섹션 |
| 7 | **실화면 스크린샷** — best-effort | 실행 중인 dev 앱 + 브라우저 도구가 가용할 때만. 실패해도 시안 산출을 막지 않는다 — 4번의 코드 참조가 최소선 |

추출은 시안 대상 화면의 **영향 반경에 한정**한다 — 디자인 시스템 전체를 덤프하지
말 것. 시안에 테이블이 없으면 테이블 어휘는 생략해도 된다.

## 2. DESIGN.md 해석 — 인라인형 vs 포인터형

프로젝트 DESIGN.md 는 포맷이 이질적이다(실측 3종). 진입점은 항상 DESIGN.md 지만
값의 위치가 다르다:

- **인라인형** (예: ADMap 438줄, review-radar 86줄): 토큰 표·하드룰이 문서 안에
  있다. 그대로 쓴다. 단 문서가 "충돌 시 실구현 우선"을 명시하면 코드를 정본으로.
- **포인터형** (예: Intelligence-Auth 58줄): 문서는 원칙·경로 포인터만 담고 값은
  코드에 산다("SSOT 는 코드다"). **가리키는 파일을 반드시 Read** 해 실값을
  확보한다 — 포인터만 읽고 값을 추측하면 이 계약 전체가 무너진다.
- 혼합이면 항목별로 위 두 규칙을 적용한다.

## 3. DESIGN.md 부재 폴백

DESIGN.md 가 없거나 있어도 부실하면(토큰도 포인터도 없음):

1. **코드 직접 스캔으로 추출을 시도한다** — `theme.*`·`globals.css`·`tailwind.config.*`·
   대표 페이지/컴포넌트 파일에서 1·2·5·6번 항목을 재구성. 스캔도 영향 반경 한정.
2. **부재 사실을 보고에 명시한다** — "DESIGN.md 없음, 코드 스캔으로 추출" 을 침묵
   생략하지 않는다.
3. **백필을 제안한다** — 추출한 context 가 곧 DESIGN.md 초안의 재료다. 사용자에게
   생성 여부를 묻는다(자동 생성 금지 — 프로젝트 문서는 사용자 소유).

스캔조차 소득이 없으면(디자인 시스템 자체가 없는 신규 프로젝트) §6 의 net-new
경로로 간다.

## 4. 4축 충실 계약

시안은 다음 4축을 지킨다. 시안의 목적이 "구현 후 모습의 예고"이므로, 각 축의
위반은 곧 예고의 거짓이다:

1. **토큰 일치** — 색·radius·font·spacing 은 추출한 토큰 실값만 쓴다. 새 hex/px
   발명 금지. 토큰에 없는 값이 꼭 필요하면(예: 시안 전용 주석 배경) 시안 안에
   `/* non-token: <이유> */` 로 표기하고 보고에 노출한다.
2. **컴포넌트 어휘 재사용** — 기존 화면에 카드·테이블·뱃지가 있으면 그 구조·class
   감각을 재사용한다. 시안이 새 컴포넌트 스타일을 발명하면 구현자는 "이걸 새로
   만들라는 뜻인가?" 를 놓고 매번 갈린다.
3. **레이아웃 밀도** — 대표 실화면의 정보 밀도·여백 감각을 따른다. 시안만 과장되게
   화려하면(그라데이션·대형 히어로) 구현이 초라해 보이는 착시를 만든다.
4. **기술 제약 반영** — 실스택이 표현하지 못하는 것은 시안에도 넣지 않는다(예:
   해당 프로젝트가 CSS 프레임워크 미사용이면 Tailwind 표기 금지, 서버 렌더 테이블에
   가상 스크롤 시연 금지).

## 5. 검증 — 기계 + 사람

**기계 (토큰 부분집합 체크).** 시안을 쓴 직후 실행한다:

```bash
bash ~/.claude/skills/mockup/scripts/check-tokens.sh <mockup.html> <tokens.txt>
```

`tokens.txt` 는 1번 항목에서 추출한 허용 색값(한 줄에 하나, hex). 스크립트는 시안
내 모든 hex 를 정규화(소문자·3자리 확장)해 대조하고, 집합 밖 값을 위반으로
보고한다(`non-token` 표기 라인은 면제). **위반 = 수정 후 재실행** — 통과할 때까지.
프로젝트에 자체 `design-lint` 류가 있으면 그것도 함께 돌린다. 스크립트가 못 보는
것(px 수치·class 오용)은 4축 계약을 직접 대조한다.

**사람 (실화면 대조).** 시안 리뷰를 요청할 때 4번 항목의 대표 실화면 참조(파일
경로, 있으면 스크린샷)를 시안과 **나란히 제시**한다 — 리뷰어가 "기존 화면과 같은
제품으로 보이는가"를 즉석에서 판정할 수 있게. 시안만 단독으로 보여주면 괴리는
구현 후에야 발견된다.

## 6. net-new UI — 전문 스킬 위임 시 계약 주입

시안 대상에 재사용할 기존 화면 어휘가 없으면(신규 프로덕트·첫 화면) 자유 창작이
필요하다 — `frontend-design`(고품질 창작)·`prototype`(다안 비교) 등 전문 스킬로
위임을 제안한다(`AskUserQuestion`, 자동 시작 금지). 단:

- 토큰이 **존재하면**(디자인 시스템은 있는데 이 화면류가 처음) 위임 프롬프트에
  추출한 토큰 집합·하드룰을 **계약으로 주입**하고, 결과물에도 §5 기계 검증을
  돌린다 — 전문 스킬의 미감 능력과 토큰 충실은 양립한다.
- 토큰도 없으면(§3 폴백 무소득) 자유 창작 그대로 — 이때 시안이 곧 디자인 시스템의
  씨앗이므로, 산출 후 DESIGN.md 백필 제안을 한다.
