# Parse DESIGN.md & Build the Theme

DESIGN.md 를 읽어 token 을 발견하고, 그것을 단일 token 정의 파일 + Tailwind 매핑으로
바꾸는 단계. 핵심 원칙: **스키마를 가정하지 말고 실제 파일에서 발견하라.**

## 1. DESIGN.md 파싱 — 발견, 가정 금지

design-extractor 의 `DESIGN.md` 는 사람이 읽는 마크다운이다 — 추출마다 구조가
조금씩 다를 수 있다. 고정 스키마를 코드로 박지 말고, 실제 파일을 읽어 아래 카테고리를
*발견*하라. 흔히 담기는 것:

- **Colors** — primary/secondary/accent/background/surface/text/border 등. hex,
  rgb, 혹은 named scale(예: `gray-50`…`gray-900`). 다크/라이트 변형이 있을 수 있다.
- **Typography** — font family, size scale, weight, line-height, letter-spacing.
- **Spacing** — 간격 scale(4/8/12/16…), 혹은 named(sm/md/lg).
- **그 외 가끔** — border-radius, shadow, breakpoint, z-index. 있으면 token 으로
  잡고, 없으면 Derive 단계에서 합성한다([`traceability.md`](traceability.md)).

발견한 것을 **token 인벤토리**로 사용자에게 보고하라 (REQ-F-001 의 acceptance):

```
DESIGN.md 에서 발견한 token:
  colors      : 14 (primary, surface, text-primary, … + gray scale 9)
  typography  : font 2, size 7, weight 3
  spacing     : 8-step scale
  radius      : 없음 → derive 예정
  shadow      : 2 (sm, lg)
```

없거나 깨진 파일이면 명확히 에러를 내고 멈춘다 — 빈 token 으로 진행하지 말 것.

## 2. token 이름 정규화

원본 이름을 최대한 보존하되, CSS 변수/Tailwind 키로 쓸 수 있게 kebab-case 로
정규화한다. 의미를 바꾸지 말 것 — `Primary Button BG` → `--color-primary-button-bg`,
이름을 짧게 "개선"하지 않는다(원본 충실).

scale 류(gray-50…900, spacing 1…8)는 그 단계 번호를 유지한다.

## 3. tokens.css — raw 값이 사는 유일한 곳

발견·정규화한 모든 token 을 `:root` 의 CSS custom property 로 쓴다. **이 파일이
raw hex/px 가 합법적으로 존재하는 단 하나의 장소다.**

```css
/* theme/tokens.css — generated by imprint from <DESIGN.md path> */
/* 모든 raw 값은 여기에만 산다. 다른 파일은 var(--token) 으로 참조한다. */
:root {
  /* --- from DESIGN.md (extracted) --- */
  --color-primary:        #635bff;
  --color-surface:        #ffffff;
  --color-text-primary:   #1a1f36;
  --font-sans:            "Inter", system-ui, sans-serif;
  --text-base:            16px;
  --space-4:              16px;
  --shadow-sm:            0 1px 2px rgba(0,0,0,.06);
  /* --- derived (DESIGN.md 에 없어 합성, traceability.md 규칙) --- */
  --color-primary-hover:  #5249e0;   /* derived: primary L-8% */
  --radius-md:            8px;        /* derived: space-4 ÷ 2 */
}
```

- DESIGN.md 에서 온 것과 derived 를 **주석으로 명확히 분리**한다 — 사용자가
  "원본 vs 내 추정" 을 한눈에 본다.
- 각 derived token 은 *무엇에서 어떻게* 파생했는지 인라인 주석을 단다.
- DESIGN.md 의 모든 token 이 여기 1:1 로 있어야 한다(누락 0 = REQ-F-002 acceptance).

## 4. tailwind.config.js — named token 매핑 (raw 값 없음)

Tailwind 테마를 CSS 변수로 확장해, 컴포넌트가 `bg-primary` `text-text-primary`
`rounded-md` `p-4` 같은 *의미 있는 클래스*를 쓰게 한다. **여기에는 raw hex/px 가
없다 — 전부 `var(--token)` 참조.**

```js
// theme/tailwind.config.js — generated by imprint
/** @type {import('tailwindcss').Config} */
module.exports = {
  content: ["./components/**/*.{tsx,jsx}", "./preview.html"],
  theme: {
    extend: {
      colors: {
        primary:       "var(--color-primary)",
        "primary-hover":"var(--color-primary-hover)",
        surface:       "var(--color-surface)",
        "text-primary":"var(--color-text-primary)",
      },
      fontFamily:   { sans: "var(--font-sans)" },
      fontSize:     { base: "var(--text-base)" },
      spacing:      { 4: "var(--space-4)" },
      borderRadius: { md: "var(--radius-md)" },
      boxShadow:    { sm: "var(--shadow-sm)" },
    },
  },
};
```

이 매핑 덕에 traceability 검증이 단순해진다: 컴포넌트/시안은 클래스명만 쓰고,
클래스는 var 로, var 는 tokens.css 한 곳으로 모인다. raw 값을 찾으려면 tokens.css
하나만 신뢰 경계로 두면 된다.

## 5. 누락 확인 (theme verify)

테마 작성 후 DESIGN.md token 인벤토리와 대조한다: 발견한 모든 token 이 tokens.css
에 entry 가 있는가? 하나라도 빠지면 그 token 은 영영 안 쓰이게 되어 충실성이
깨진다 — 누락 0 을 확인하고 다음(Derive/Components)으로 간다.
