# deep-prompt — 자율 실행용 Goal Prompt 저작

사용자가 "이걸 백그라운드로 돌리고 싶다"는 한두 문장을 들고 온다. 그걸 그대로
goal 칸에 넣으면 자율 에이전트는 *언제 끝났는지 모른 채* 표류한다 — 영원히 루프를
돌거나, 절반만 하고 멈추거나, 범위를 넘어 엉뚱한 걸 건드린다. 자율 실행의 실패는
거의 항상 **약한 성공 기준**에서 온다: 사람이 옆에 있으면 "이 정도면 됐어"를
판단해주지만, 백그라운드 잡에는 그 사람이 없다.

이 스킬은 흐릿한 의도를, 에이전트가 **혼자서 완료를 판정하고 루프를 빠져나올 수
있는** 고정 구조의 Goal Prompt 로 바꿔 `.md` 파일로 저장한다. 핵심 작업은 글쓰기가
아니라 **성공 기준을 측정 가능하게 못 박는 것**이다 — 나머지 섹션은 그 기준을
지지하는 받침대다.

## 이것이 올바른 도구일 때

- 사용자가 어떤 작업을 **백그라운드/자율 goal 로 돌릴** 프롬프트를 원할 때.
- 산출물이 **goal 칸에 붙여넣을 텍스트 한 덩어리**(`.md`)일 때.
- goal 의 결과물이 **UI/화면**이면 — 그 화면을 self-contained HTML 시안으로도
  함께 산출해 자율 에이전트의 *시각 타겟*으로 박는다(§3.5, 조건부). 비-UI goal
  (API·테스트·데이터·인프라·문서)이면 시안 없이 `.md` 만.

손대지 말아야 할 때:

- 아이디어가 **정말로 모호하고 커서** 무엇을 만들지 자체가 안 정해졌을 때 →
  `deep-interview` 로 먼저 결정화. deep-prompt 는 *짧은* 명료화만 한다, 풀
  Socratic 인터뷰가 아니다.
- 지금 당장 **기능을 빌드/수정/디버그**할 때 → `forge`/`renew`/`hunt`. 이
  스킬은 작업을 *수행*하지 않는다; 자율 에이전트에게 줄 *지시문*을 쓴다.

## 왜 이 형태인가 — 자율성의 조건

goal 프롬프트는 사람이 지켜보지 않는 동안 에이전트가 가진 **유일한 계약**이다.
일반 대화는 막히면 사용자에게 물어보면 되지만, 백그라운드 잡은 물어볼 사람이 없는
구간을 견뎌야 한다. 그래서 세 가지가 본문에 명시적으로 박혀 있어야 한다:

1. **완료가 무엇인지** (Success Criteria) — 에이전트가 스스로 체크해 루프를 끝낼
   수 있는, 관찰 가능한 조건. 이게 약하면 자율 실행 전체가 무너진다.
2. **건드리면 안 되는 것** (Constraints) — 사람이 없으니 가드레일이 본문에
   있어야 한다. 특히 비가역·외부발신 작업의 경계.
3. **완료/막힘을 실행기에 어떻게 신호하는가** (Done & Report) — 백그라운드 잡
   분류기는 실행 에이전트의 **메시지 텍스트만** 읽어 상태를 판정한다(tool 출력·
   subagent 보고는 안 본다). 그래서 goal 프롬프트는 실행기에게 리터럴 완료 신호
   (`result:`)와 막힘 신호(`needs input:` / `failed:`)를 **명령**해야 한다. 이
   토큰을 안 박으면 잡이 끝나도 "완료"로 분류되지 않아 표류한다.

## 워크플로

순서대로. 추론으로 채울 수 있는 칸은 채우고, 자율 실행을 위태롭게 하는
빈칸만 물어라.

### 1. 입력에서 목표 추출 (있으면 안 묻는다)

사용자의 한두 문장에서 다음을 뽑아낸다. 이미 말한 건 다시 묻지 말고 확인만:

- **무엇을 달성하나** — 한 문장 동사구. ("로그인 플로우에 rate limit 추가",
  "스테이징 깨진 e2e 테스트 전부 초록으로", "이 디렉토리 문서 최신화").
- **어디서 도나** — 레포/경로/환경. brownfield 면 건드릴 영역만 가볍게
  Read/Grep 으로 확인한다(전체 레포 스캔 금지) — 근거 있는 Context·Constraints 를
  쓰기 위해서다.
- **어떻게 끝났다고 아나** — 가장 중요하고 가장 자주 비어 있는 칸. 사용자가
  완료 신호를 말하지 않았으면 여기를 물어라.

### 2. 단 하나만 물어라 — 측정 가능한 완료 조건. 나머지는 안전 기본값.

과잉 인터뷰와 과소 인터뷰는 같은 실수에서 온다 — **무엇이 진짜 must-ask 인지**를
안 가르는 것. 규칙은 단순하다:

**유일한 must-ask** — 입력에서도 코드를 가볍게 읽어서도 **측정 가능한 완료 조건**을
끌어낼 수 없을 때. 이게 비면 자율 루프가 못 끝난다. 사용자가 완료 신호를 안 줬고
추론도 안 되면, 이것만 물어라("어떻게 끝났다고 판정하죠 — 통과시킬 명령/테스트나
관찰할 출력은?"). 보통 1라운드면 충분하다.

**나머지는 묻지 말고 안전 기본값으로 채우고 명시한다** — 묻는 순간 과잉이다:

| 빈칸 | 묻지 말고 이렇게 | 명시 위치 |
|---|---|---|
| 건드리면 안 되는 영역 | 입력이 지목한 영역만 수정, 그 밖은 읽기만 | Constraints |
| 비가역/외부발신 (push·배포·삭제·메일) | **금지 — 변경만 두고 보고** (가장 안전) | Constraints |
| 스타일·네이밍 | 기존 코드 관습 따름 | (자명, 생략 가능) |
| Context 세부 | 입력이 지목한 영역만 Read/Grep 으로 채움 | Context |

안전 기본값이 사용자 의도와 다를 수 있는 단 하나의 위험은 "사실은 push/배포까지
원했다"인데, 그건 **덜 위험한 쪽으로 틀린 것**이다(사람이 나중에 푸시하면 됨). 반대로
기본을 "push 허용"으로 두면 사람 없는 동안 사고가 난다. 그래서 기본은 항상 금지.

deep-interview 와의 선 긋기: must-ask 1개를 물었는데도 답이 또 모호해 2~3라운드로
번지면, 이건 deep-prompt 가 아니라 결정화가 필요한 신호다 — `deep-interview` 를
권하고 멈춰라. 이 스킬은 *이미 대체로 명확한* 의도를 아티팩트로 굳히는 것이지,
모호함을 파고드는 게 아니다.

### 3. 고정 템플릿 채우기

아래 골격을 *정확히 이 섹션 순서로* 채운다. 모든 goal 프롬프트가 일곱 섹션을 다
쓰는 건 아니다 — Out of Scope 가 자명하면 뺄 수 있다 — 하지만 **Objective /
Success Criteria / Done & Report 세 개는 절대 빼지 마라**. 그게 자율성의 척추다.

```markdown
# Goal: <한 줄 제목>

## Objective
<달성할 것 한 문장. 동사로 시작. 모호한 형용사("개선", "정리") 금지 —
관찰 가능한 결과로.>

## Success Criteria
<에이전트가 스스로 체크해 루프를 끝낼 수 있는 조건. 각 항목은 검증 가능해야
한다 — 명령을 돌리거나 파일을 보거나 출력을 확인해 참/거짓이 갈려야 한다.>
- [ ] <검증 가능한 조건 1 — 예: `npm test` 가 0 exit>
- [ ] <검증 가능한 조건 2 — 예: `POST /login` 11번째 요청에 429 반환>

## Context
<레포, 관련 경로(file:line), 현재 상태, 환경. 에이전트가 맨바닥에서 시작한다고
가정하고 필요한 좌표를 준다. 추측 금지 — 읽고 확인한 것만.>

## Constraints
<사람 없이 도는 동안의 가드레일. 무엇을 건드리지 말지, 범위 경계,
비가역·외부발신 작업 정책.>
- <예: `src/legacy/` 는 읽기만, 수정 금지>
- <예: 커밋·푸시·PR 생성은 하지 말 것 — 변경만 두고 보고>

## Verification
<완료를 확인하는 정확한 명령·테스트. Success Criteria 와 1:1로 대응.
에이전트가 이걸 돌려 자가 판정한다.>

## Out of Scope
<명시적 비목표 — 범위 넘침 방지. 자명하면 생략 가능.>
- <예: 기존 테스트 리팩터링은 하지 않음>

## Done & Report
이 goal 은 사람이 지켜보지 않는 백그라운드 잡으로 실행된다. 분류기는 네
**메시지 텍스트만** 읽으니(tool 출력·subagent 보고는 안 읽힘) 검증 결과·변경 요약을
반드시 텍스트로 다시 적어라. 신호는 아래 리터럴 토큰을 각각 한 줄로 emit 한다:
- 완료 — 위 Success Criteria 가 **전부 참**이면, 마지막 메시지를 `result:` 로
  시작하는 한 줄로 맺어라(달성 내용 + 핵심 수치). 이게 유일한 완료 신호다 —
  "done"·"완료" 같은 산문은 신호로 안 잡힌다.
- 막힘 — 사람의 한 가지 행동(권한·결정·접근)이 있어야만 진행 가능하고 합리적
  추측이 불가능하면, `needs input:` 한 줄에 정확히 무엇이 필요한지.
- 불가 — 전제가 틀렸거나 구조적으로 불가능하면(잘못된 레포·없는 바이너리 등),
  `failed:` 한 줄에 이유.
그 외에는 계속 진행한다 — Verification 을 돌려 Success Criteria 를 자가 판정하고
전부 참이 될 때까지 루프한다.
```

> 위 Done & Report 블록의 세 토큰(`result:` / `needs input:` / `failed:`)은
> **글자 그대로** 생성물에 박는다 — 실행기가 emit 할 신호이지 네가 다듬을 산문이
> 아니다. Success Criteria 와 `result:` 의 연결("전부 참이면 result:")이 자율 루프의
> 종료 조건을 런타임 완료 신호에 묶는 다리다.

### 3.5 산출물이 UI/화면이면 — self-contained HTML 시안 동반 (조건부)

**판정 게이트 먼저.** goal 의 결과물이 사람이 보는 화면인가 — 페이지·컴포넌트·
대시보드·패널·모달·레이아웃·시각 출력? **그럴 때만** 이 단계를 한다. API 필드
추가·테스트 초록·데이터 인제스트·문서·리팩터·인프라 goal 이면 시안 대상이 아니므로
**통째로 건너뛰고 §4 로** 간다. 억지로 시안 만들지 말 것(비-UI 에 시안은 노이즈).

UI goal 이면, goal 프롬프트와 **같은 디렉토리**에 `<slug>-mockup.html` 로 단일
self-contained HTML 시안을 쓴다. 시안 작성 규칙(외부 asset 0·전부 인라인·핵심
요소와 레이아웃·상태별 정적 섹션·brownfield 디자인 토큰 매칭)은 파이프라인의 HTML
companion 규약이 SSOT 다 — `~/.claude/skills/craft-core/references/pipeline.md` Phase 1 의
리뷰 친화적 HTML companion 섹션을 따르라(여기 복제하지 않는다). 목적만 다르다:
pipeline/deep-plan 의 companion 이 사람 리뷰용이라면, 여기 시안은 자율 에이전트가
*무엇을 만들지* 합의하는 시각 타겟이다(픽셀 완벽 불필요).

시안을 쓴 직후 **`Artifact` 도구로 publish** 하고 사용자에게 artifact URL 을
제시한다 — 사용자가 goal 승인 전 시각 타겟을 링크로 리뷰한다. 로컬 파일은 유지
(에이전트 입력). 규칙 SSOT: `~/.claude/rules/html-mockup-artifact.md`.

그리고 **시안을 goal 프롬프트에 묶는다** — 시안은 장식이 아니라 성공 기준의 일부다
(이하 deep-prompt 고유):

- **Context** 에 시안 경로를 박는다: `UI 시각 타겟: <slug>-mockup.html (이 레이아웃·요소 기준)`.
- **Success Criteria** 에 시안 대조 항목을 1개 이상 넣는다 — 단 §4 게이트를 통과하는
  *관찰 가능한* 형태로. "시안과 똑같이"(✗ 주관적) 대신 "시안에 있는 요소 X·Y·Z 가
  렌더 DOM 에 존재"·"빈/에러 상태가 시안의 두 정적 섹션과 대응"처럼 체크 가능하게.

### 4. 검증 가능성 게이트 — 항목마다 5질문, 하나라도 No 면 다시 써라

산출물 품질이 들쭉날쭉한 가장 큰 원인은 이 게이트를 건너뛰는 것이다. 저장 전,
**Success Criteria 의 각 항목**을 다음 5질문에 하나씩 통과시킨다 — 통과 못 하면
그 자리에서 관찰 가능한 조건으로 고쳐 쓴다:

1. **관찰 가능한가** — 사람 판단 없이 명령 출력·파일 내용·종료 코드로 참/거짓이
   갈리나? ("안전해짐" ✗ / "11번째 요청에 429" ✓)
2. **Verification 짝이 있나** — 이 기준을 확인할 정확한 명령/관찰이 Verification
   섹션에 있나? 짝 없으면 에이전트가 체크 못 한다.
3. **에이전트 권한 안인가** — 가진 도구·접근으로 실제 확인 가능한가? (외부
   대시보드를 봐야 알면 자율 판정 불가.)
4. **이분법인가** — 부분 충족이 모호하지 않나? "대부분 테스트 통과"는 회색지대 →
   "모든 테스트 통과".
5. **루프를 끝내나** — 이 기준들이 다 참이면 에이전트가 *멈춰도 되나*? 멈춤을
   정당화 못 하면 기준이 빠진 것.

좋은 예: `tests/auth/ 의 모든 테스트가 pass`, `429 가 11번째 요청에 반환`,
`grep -rn "validateInput" src/routes/ → 0 매치`.
나쁜 예: `로그인이 더 안전해짐`, `코드가 더 읽기 쉬워짐`, `성능 개선`.

작동하는 goal 프롬프트 2개와 약한 것을 고친 before/after 가 필요하면
`references/examples.md` 를 읽어라.

### 5. 저장 — 경로 확인 후 쓰기

`.md` 파일로 저장한다. 사용자가 경로를 줬으면 그대로. 안 줬으면 제안하고
쓰기 전에 확정받아라 (비가역까진 아니지만 위치는 사용자 결정):

- 레포에 `docs/` 컨벤션이 있으면 `docs/goals/<slug>.md` 제안.
- 없으면 `goal-prompts/<slug>.md` 또는 사용자 지정 위치.
- 파일명 `<slug>` 는 Objective 에서 kebab-case 로.
- §3.5 에서 시안을 만들었으면 `.md` 와 **같은 디렉토리**에 `<slug>-mockup.html` 로 함께 쓴다.

쓴 뒤 `~/.claude/skills/craft-core/references/output-contract.md` 의 종료 블록으로
보고한다 — `result:` 한 줄(무엇을 위한 goal 인지) + `프롬프트` 행의 상대경로와 `open`
명령(L1+L2). 시안을 만들었으면 그 행도 추가한다. 그다음 그 내용을 goal 칸에
붙여넣어 백그라운드 잡으로 돌리면 된다고 안내하라. 예:

```
result: <topic> goal prompt 산출 — 검증 가능한 성공 기준 N개 (+UI 시안)

산출물 — 열기:
- 프롬프트 `goal-prompts/<slug>.md`       →  `open goal-prompts/<slug>.md`
- UI 시안 `goal-prompts/<slug>-mockup.html`  →  `open goal-prompts/<slug>-mockup.html`

(`open` = macOS. Linux `xdg-open`, Windows `start`.)
```

(비-UI goal 이면 시안 행 없이 프롬프트 한 줄만.)

## Anti-patterns

- **검증 불가 성공 기준** — "잘 되면 끝"은 자율 에이전트에게 무한 루프 또는
  조기 종료를 뜻한다. 모든 기준은 명령/관찰로 판정 가능해야 한다. 이게 이
  스킬의 존재 이유다.
- **신호 토큰 누락** — Done & Report 에 `result:`/`needs input:`/`failed:` 리터럴을
  안 박고 "완료 시 보고" 같은 산문으로 두기. 그러면 잡이 끝나도 분류기가 완료로
  못 잡아 표류한다. 토큰은 글자 그대로, Success Criteria 전부 참 → `result:` 로 묶어라.
- **과잉 인터뷰** — 가드레일·범위·스타일을 일일이 묻기. 이건 안전 기본값으로 채울
  것(§2). must-ask 는 측정 가능한 완료 조건 하나뿐. 그것도 답이 또 모호해 2~3라운드로
  번지면 멈추고 `deep-interview` 로 보내라.
- **가드레일 누락** — 비가역·외부발신 작업(push, 배포, 삭제, 메일)을 Constraints
  에 안 박으면 사람 없는 동안 사고가 난다. 의심되면 "변경만 두고 보고"로 막아라.
- **Context 추측** — 읽지 않은 경로·함수를 단언. 에이전트는 그 좌표를 믿고
  움직인다 — 틀리면 처음부터 헛돈다. Read/Grep 으로 확인한 것만 써라.
- **Objective 에 형용사** — "개선/정리/최적화"만 적으면 무엇이 완료인지 비어
  있다. 관찰 가능한 결과 동사로.
- **비-UI goal 에 시안 강제 / 시안을 SC 에 안 묶기** — §3.5 는 UI 결과물 한정.
  API·테스트·데이터·인프라 goal 에 HTML 시안은 노이즈다. 또 시안을 만들고도
  Success Criteria 에 *관찰 가능한* 대조 항목으로 묶지 않으면 장식일 뿐 — 자율
  에이전트가 무시한다. "시안과 똑같이" 같은 주관적 기준도 §4 게이트에서 탈락.
