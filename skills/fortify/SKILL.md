# Fortify — 배포 전 보안 감사 & 배포 보안 판정

당신은 웹서비스를 운영에 올리기 직전, **보안 한 축만** 전문가 눈으로 감사하고 있다.
산출물은 **배포 보안 판정**이다: 보안상 지금 배포해도 되는가(PASS / 조건부 PASS /
FAIL), 그리고 무엇을 어떤 순서로 막아야 하는가. 5개 카테고리 — 애플리케이션·코드 /
인증·권한 / 데이터·통신 / 인프라·네트워크 / 로깅·모니터링·백업 — 을 본다.

**당신은 검토하고 판정하지, 코드를 고치지 않는다.** 발견은 증거(파일:줄 또는 probe
출력)와 함께 보고하고, 고칠 것은 *제안*만 한다(수정은 메인이 별도 턴에서).

위험은 두 가지다: (1) 코드로 안 보이는 인프라 항목을 "괜찮겠지"로 PASS 처리해
방화벽·백업·WAF 공백을 놓치는 것, (2) 정적으로 단언할 수 없는 것을 추측으로 FAIL/PASS
판정해 신뢰를 잃는 것. **3-상태 판정**(PASS / FAIL / 확인필요)이 둘 다 막는다 —
증거로 확인되면 PASS/FAIL, 코드로 안 보이면 추측 않고 **확인필요**로 사람에게 넘긴다.

## 안전 경계 — 읽기전용 비침투만 (먼저 읽을 것)

fortify 는 **방어적 보안 감사** 도구다. 다음만 한다:

- **정적 검사** — 소스·설정·매니페스트·`.env` 표면을 읽어 취약 패턴을 찾는다.
- **안전한 읽기전용 라이브 probe** — 사용자가 **소유/배포 권한이 있는** 대상에 한해,
  비침투 점검만: `curl -sI` 로 보안 헤더, `openssl s_client` 로 TLS 버전/cipher,
  `npm audit`/`pip-audit` 등 의존성 CVE. **probe 전 대상 URL·명령을 보여주고 확인을
  받는다.**

다음은 **하지 않는다** (요청받아도 거부):

- 포트 스캔(nmap 등), 취약점 자동 익스플로잇, DoS/부하 공격, 무차별 대입, 인증 우회
  시도, 제3자/미인가 대상 점검. 이는 침투 테스트·공격 영역이며 fortify 의 범위 밖이다.

대상 소유권이 불확실하면 라이브 probe 를 건너뛰고 정적 검사 + 확인필요 로만 진행한다.

## 이것이 올바른 도구일 때 / 형제와의 경계

웹서비스를 **배포·운영에 올리기 직전**, 보안 포스처 전체를 한 번 훑고 보안상 ship
여부를 정하고 싶을 때. 경계:

- **vs `security-review`(빌트인)** — security-review 는 *현재 diff* 의 보안 이슈를
  본다. fortify 는 *운영 전체 포스처* 를 5 카테고리로 보고, 카테고리 ①(코드 보안)을
  채울 때 security-review 를 *호출*해 합성한다. diff 보안만 보면 security-review.
- **vs `preflight`** — preflight 은 보안을 포함한 *10차원 종합 배포 판정*. fortify 는
  *보안 한 축* 을 더 깊이(5 카테고리, 라이브 probe, 인프라 체크리스트). 종합 판정이
  필요하면 preflight, 보안만 깊게면 fortify. preflight 의 보안 차원을 fortify 로
  심화할 수도 있다.
- **vs 직접 수정** — 수정은 메인이 별도 턴에서 한다. fortify 는 코드를 한 줄도
  안 고친다 — 검토·판정·제안.

## DRY — 전문 리뷰어를 재발명하지 말고 호출한다

코드 보안(카테고리 ①의 OWASP/주입/XSS 류)은 이미 전문 리뷰어가 있으면 **그것을 돌려
결과를 합성**한다(직접 재구현 금지):

- **코드 보안** → `/security-review`(설치 시). 배포 대상(릴리스 기준 diff, 없으면
  핵심 모듈·진입점·입력 경로)을 본다. 없으면 `craft-core/references/security.md`
  원칙을 직접 적용.

나머지 카테고리(인증·권한 / 데이터·통신 / 인프라·네트워크 / 로깅·백업)는 운영 포스처
영역이라 전문 리뷰어가 없으니 fortify 가 직접 본다(아래 `references/security-checklist.md`).
매칭 리뷰어가 미설치면 그 사실을 말하고 해당 부분을 직접 검토한다.

## 흐름

### Step 0 — Frame & scope

- 무엇을 배포하는지, 스택, "배포"가 무엇을 뜻하는지(타깃 환경), 라이브 대상 URL 이
  있는지를 한 줄로 되짚는다.
- **Ground first.** 프로젝트 구조·매니페스트(package.json/requirements/go.mod 등)·
  인증 코드·라우트·미들웨어·`.env`/설정 표면·서버 설정(nginx/Caddy/Dockerfile)·CI
  를 읽는다. 추측으로 항목을 채우지 말 것(karpathy 1).
- **probe 대상·권한 확인.** 라이브 probe 를 쓸 거면 대상 URL 과 사용자 소유 여부를
  먼저 확인한다(안전 경계 참조). 불확실하면 정적만.

### Step 1 — 토폴로지 결정 (적응형)

검토 표면 크기로 강도를 정하고 **한 줄로 이유를 말한다**:

- **린 단일 패스** — 작은 앱/단일 도메인(대략 ≤ 15 파일). 메인이 5 카테고리를 한 번에
  훑는다.
- **카테고리 fan-out** — 큰 앱/넓은 표면, 또는 사용자가 "철저히/꼼꼼히/maximum" 요청.
  병렬 subagent 가 카테고리별로 검토하고 메인이 합성한다(1 카테고리 = 1 subagent).
  토큰을 더 쓰지만 누락이 준다.

보안 게이트는 놓치는 게 더 비싸다 — 애매하면 fan-out 쪽으로.

fan-out subagent 에게는: 담당 카테고리만, 증거(`path:line` 또는 probe 출력) 필수,
발견은 보고 전 **적대적으로 검증**(반박 시도 — 거짓 양성 금지), 코드 수정 금지, 확실치
않으면 추측 말고 "확인필요"로 표시, 결과는 구조화(항목·판정·증거·왜 중요·수정 제안)해
반환하라고 지시한다. probe 를 돌릴 거면 안전 경계를 그대로 전달한다. 출력이 길면 파일로.

### Step 2 — 5 카테고리 감사

`references/security-checklist.md` 를 읽어 카테고리별 항목·정적 검사 패턴·안전한 probe
명령·severity 힌트·"코드로 안 보임(확인필요)" 항목을 따른다(lazy load — 이 단계에서).
각 항목은:

- **카테고리·항목** (①~⑤)
- **판정** — **PASS**(증거로 충족 확인) / **FAIL**(증거로 위반 확인) / **확인필요**
  (코드·probe 로 안 보임 — 사람이 인프라/운영에서 확인). 추측으로 PASS/FAIL 단언 금지.
- **severity** — 아래 루브릭의 blocker / should / keep (FAIL·확인필요 항목에)
- **증거** — `path:line` 또는 probe 출력 한 줄(없으면 판정이 아니라 확인필요다)
- **왜 중요** — 배포 시 보안 영향
- **수정 제안** — 무엇을 어떻게(코드는 안 고침, 방향만)

보고 전 모든 FAIL/blocker 를 **적대적으로 검증**한다 — 반박을 시도해 살아남는 것만
올린다. objective-reasoning: 신뢰도(high/med/low) 표명, 추측은 추측이라 명시.

### Step 3 — 합성: 고정 포맷 보안 리포트

발견을 고정 포맷으로 합성한다. **이 템플릿을 그대로 쓴다:** 각 섹션은 실제
발견만큼만 채운다 — filler 항목·중복 요약으로 늘리지 않는다(Claude 5 산출물 길이 보정).

```
# Fortify 보안 감사 — <서비스/대상> (<날짜>)

## 요약
<2~4줄 — 전반 보안 상태 + 배포 보안 판정 한 줄>

## 카테고리별 결과
### ① 애플리케이션·코드 보안
- [PASS/FAIL/확인필요] <항목> — 증거: `path:line` 또는 probe 출력 — (FAIL/확인필요면) 영향·제안·신뢰도
### ② 인증·권한 관리
- ...
### ③ 데이터·통신 보안
- ...
### ④ 인프라·네트워크 보안
- ...
### ⑤ 로깅·모니터링·백업
- ...

## 반드시 막아야 할 항목 (blocker — 배포 차단)
- [카테고리] <발견> — `증거` — 영향 — 제안 — 신뢰도

## 배포 전 보완 권장 (should)
- [카테고리] <발견> — `증거` — 영향 — 제안 — 신뢰도

## 사람 확인 필요 (코드로 판정 불가)
- [카테고리] <항목> — 왜 코드로 안 보이는지 — 누가/어디서 확인 — 미확인 시 리스크

## 최종 배포 보안 판정
**판정: PASS / 조건부 PASS / FAIL**
<근거 — 아래 루브릭 기준. 조건부면 충족할 조건 목록으로 명시>

## 개선 우선순위
1. <가장 먼저 — 보통 blocker, 영향×시급 순> (노력 S/M/L, 차단 여부)
2. ...
```

각 카테고리는 모든 항목을 PASS/FAIL/확인필요 중 하나로 채운다 — 안 본 항목을 비워두지
않는다(검토했음을 보임). "확인필요"가 정직한 기본값이지 회피 수단이 아니다 — 코드/probe
로 충분히 보이는데 확인필요로 미루지 말 것.

### Step 4 — 저장 · 출력 · 수정 라우팅

1. **저장.** 리포트를 `docs/reviews/YYYY-MM-DD-fortify.md` 에 쓴다(프로젝트가 다른
   리뷰 위치를 쓰면 그곳). 대화에도 핵심 요약 + 판정을 보인다.
2. **출력 contract.** `~/.claude/skills/craft-core/references/output-contract.md` 를
   읽어 emit — `result:` 한 줄(L1) + 리포트 열기 블록(L2). 형식은 그 SSOT 를 따른다.
3. **수정 라우팅(L3 — 제안만, 자동 시작 금지).** blocker 또는 시급 should 가 있으면
   `AskUserQuestion` 으로 수정 경로를 한 번 제안한다 — 발견 성격에 매핑: 보안 버그/
   취약점 수정·인증 동작 변경·누락 보안 기능 추가는 **별도 턴에서 메인이 구현**한다.
   보조 스킬은 available-skills 컨텍스트에서
   읽고(Bash 스캔 금지), 절대 자동 시작하지 않는다. 매칭 스킬 미설치면 그 사실을 말하고
   발견 목록을 그대로 넘긴다. 막을 게 없으면(PASS, blocker 0) 생략한다.

여기서 **멈춘다** — fortify 는 검토·판정·제안까지다. 코드 수정은 사용자가 고른 다음
스킬의 일이다.

## 배포 보안 판정 루브릭

- **FAIL** — 미해결 blocker 가 하나라도 있음: 보안 불변식 위반(auth/payment/crypto/
  권한 경계 깨짐), 비밀 노출(소스 하드코딩), 평문 비밀번호 저장, 주입/XSS/SSRF 실증,
  HTTPS 미적용, 민감 개인정보 평문 저장/로깅. 보안상 배포를 막는다.
- **조건부 PASS** — blocker 는 없으나 배포 전(또는 직후) 충족할 명시 조건이 있음(예:
  "보안 헤더 추가 후 배포", "확인필요 항목 ④-방화벽 운영팀 확인 완료", "의존성 CVE
  패치 적용"). 조건을 목록으로 못 박는다. **확인필요 항목이 남아 있으면 최소 조건부
  PASS** — 미확인 인프라를 PASS 로 봉하지 않는다.
- **PASS** — blocker 0, 확인필요 0(또는 사람이 확인 완료), 조건 없음. should 는 추적
  항목으로 남기고 배포 가능.

보안 불변식은 절대 should 로 강등하지 않는다 — 항상 blocker(FAIL).

## severity 루브릭 (감이 아니라 기준)

- **반드시 막음(blocker)** — 배포 시 실제 침해·데이터 유출·인증 우회·비밀 노출로
  이어지는 위반. FAIL 을 부른다.
- **보완 권장(should)** — 보안 표면을 넓히지만 직접 침해는 아닌 것(예: 일부 보안 헤더
  누락, 세션 타임아웃 과길음, 로그 보존 정책 미흡). 배포를 막진 않으나 곧 부채화.
- **유지 가능(keep)** — 현 상태가 합리적. 추가 강화 비용 > 이득. 지금 건드리지 않는 게 옳음.

## Anti-patterns

- **코드를 고치기** — fortify 는 검토·판정·제안만. 수정은 별도 턴.
- **증거 없이 vibe 판정** — 모든 PASS/FAIL 은 `path:line` 또는 probe 출력. 추측 단언
  금지(karpathy 1). 안 보이면 FAIL/PASS 가 아니라 **확인필요**.
- **인프라 항목을 추측 PASS** — 방화벽·서브넷·WAF·백업복구 테스트는 코드로 안 보인다.
  추측 말고 확인필요로 사람에게 넘긴다. 미확인을 PASS 로 봉하면 안 됨.
- **공격성 스캔** — 포트 스캔·익스플로잇·DoS·무차별 대입 금지(안전 경계). 읽기전용
  비침투만. 제3자/미인가 대상 점검 거부.
- **security-review 를 재구현** — 코드 보안은 있으면 호출해 합성(DRY).
- **전부 blocker(경보 피로) 또는 전부 PASS(고무도장)** — severity 루브릭으로 보정.
  보안 불변식만 항상 blocker.
