# Linear Groom — 기존 백로그를 프로젝트로 묶고 설명을 보강

흩어진 Linear 이슈를 **읽고 → 분류하고 → 프로젝트로 묶고 → 빈약한 설명을 코드·메모리
근거로 채운 뒤 → 표로 제안하고 → 승인받아 일괄 반영**한다. 네 가지 갭을 메운다:

1. **그룹핑 갭** — 프로젝트에 안 붙은 고아 이슈를 알맞은 프로젝트로 배정.
2. **재배치 갭** — 이미 프로젝트/마일스톤이 붙었지만 내용과 어긋난 이슈를 맞는 곳으로
   옮기고, 이동으로 무효가 되는 마일스톤 소속을 정리.
3. **보강 갭** — 스크린샷-only/빈칸/한 줄짜리 이슈를 착수 가능한 spec 으로 보강.
4. **프로젝트 위생 갭** — 이슈가 전부 닫혔는데 진행형으로 남은 프로젝트·빈 프로젝트의
   상태를 사실에 맞춘다(Step 3d).

## 핵심 불변식 (먼저)

- **모든 write 는 승인 게이트 뒤.** 이슈/프로젝트는 외부 상태다. 바꿀 것을 **표로 먼저**
  보이고 사용자가 동의한 뒤에만 `save_issue`/`save_project` 를 친다. 추측으로 쏟지 않는다.
- **승인 = 실행 신호.** 게이트는 write 를 *막는* 장치지 스킬의 *종료점*이 아니다. 동의를
  받으면 되묻지 말고 같은 턴에 Step 5 로 넘어가 반영까지 끝낸다. 표만 내고 멈추면 백로그는
  한 글자도 안 바뀐 채 사용자가 손으로 옮겨야 한다 — 그루밍의 가치는 반영에서 나온다.
- **반영은 재조회로 확인.** `save_issue` 가 에러 없이 돌아온 것은 "호출됨"이지 "반영됨"이
  아니다(특히 project 를 이름 문자열로 넘겼을 때 — 동명·오탈자면 조용히 어긋난다). Step 5
  끝에서 대상 이슈를 다시 읽어 실제 필드를 눈으로 확인한 것만 완료로 보고한다.
- **원본 보존 — 코멘트로 이관.** 작성자가 넣은 스크린샷·문장은 한 글자도 잃지 않는다.
  단 본문이 아니라 **이슈 코멘트로 1회 옮긴다**(구 `## 원본 (작성자 입력)` 본문 섹션은
  폐지 — 본문은 register 헤딩 화이트리스트·600자 계약을 따라야 하고, 코멘트는 그 계약
  밖이라 스크린샷을 통째로 담을 수 있다). **순서 고정: 코멘트 먼저, 본문 교체 나중** —
  뒤집으면 코멘트 실패 시 원본이 사라진다. 이미 이관한 이슈는 재이관하지 않는다.
- **OPEN 이슈만.** Done/Canceled 는 건드리지 않는다 — 닫힌 이슈 그루밍은 헛 write 다.
- **멀쩡한 이슈는 그대로.** 이미 구조가 있는 이슈는 갈아엎지 않는다(surgical).
  구조 = register 화이트리스트(`## 작업 내용`/`## 수용 기준`/`## 추천`) **또는 레거시
  헤딩**(`## 배경`·`## 현황`·`## 원본` — 2026-07-31 이전 등록분). **레거시 헤딩도 계속
  healthy 신호로 인정한다** — 안 그러면 기존 백로그 전체가 하루아침에 보강 대상으로
  뒤집혀 전수 재작성이 된다(소급 수정 금지).
  단 본문이 멀쩡해도 **배치**(project/milestone)가 내용과 어긋나면 재배치 대상이다 —
  그때도 본문(description)은 건드리지 않고 배치 필드만 옮긴다.
- **근거 있는 것만 단언.** 파일 경로·현황은 실제로 읽은 것만. 못 본 건 "확인 필요"로.

## 실행 모드

- **interactive (기본)** — 아래 워크플로 전체. Step 4 승인 → Step 5 반영 → Step 6 검증.
- **scan-only** — 승인할 사람이 없는 주기 automation·백그라운드 실행용. Step 0~3 은 동일하게
  돌지만 Step 4 의 표를 **지정 Linear 이슈에 코멘트로 남기고 종료**한다(Step 5·6 미실행,
  `save_issue`/`save_project` 전면 금지). 진입은 호출 프롬프트에 `scan-only` 가 명시됐을
  때만 — 무인처럼 보인다고 스스로 내려가지 않는다. 상세는
  `references/scan-only.md`(진입·허용 write·코멘트 포맷·no-op 규칙)를 읽고 따른다.

## 워크플로

### Step 0 — Linear MCP 감지

`references/craft/linear.md` §1(MCP 감지/미설치 가이드/미인증 안내)을 그대로 따른다
— 그 파일이 있으면 lazy-read, 없으면 최소 확인: available tools 에 `mcp__linear*` 가
있는지 보고, deferred 면 `ToolSearch(query:"linear")` 로 로드. 미설치/미인증이면 한 번
안내하고 멈춘다(막지 말 것). 도구 이름은 워크스페이스마다 다르니 추측 호출 금지.

### Step 1 — 현재 상태 조회

추측하지 말고 실제로 읽는다:

- **팀 스코프 + 미완 이슈 전수 수집** —
  `~/.claude/skills/linear-register/references/backlog-scan.md`(공유 SSOT) §A·§B 를
  읽고 그대로 적용한다(복제 금지 — 페이지네이션·대형 응답 오프로드 처리 포함). 잘린
  채 그루밍하면 남은 고아·빈약 이슈가 조용히 빠진다.
- `list_projects {team}` → 기존 프로젝트의 `name`/`summary`/`description`/`state` 를
  확보(그룹핑 매핑 기준 + Step 3d 위생 판정 기준).
- 상세 fetch 는 backlog-scan §C 정책 — `enrichTier` 판정에는 list 의 description 으로
  충분하지만, **보강 대상으로 확정된** 이슈는 `get_issue {id}` 로 잘리지 않은 전체
  본문을 다시 받아 원본 보존이 정확하게 되도록 한다.

### Step 2 — 결정론 분류 (스크립트)

매번 손으로 재발명하지 말고 번들 스크립트로 버킷을 가른다:

```bash
node <skill>/scripts/triage-issues.mjs '<list_issues JSON>'
# 또는: echo "$JSON" | node <skill>/scripts/triage-issues.mjs
```

출력: `groupingGaps`(프로젝트 없음) · `enrichmentGaps`(`enrichTier: empty|shallow`) ·
`healthy`(손 안 댐) · `skippedClosed`(Done/Canceled). 한 이슈가 두 갭에 동시에 들 수 있다
(예: 고아 + 스크린샷-only). 각 행에는 `project`·`milestone` 현재값이 실려 나온다 —
Step 3a-2 재배치 검토가 이 값을 기준으로 대조한다(배치 적합성 자체는 모델 판단이라
스크립트 버킷이 아님). 로직·tier 정의는 `scripts/triage-issues.mjs` 주석 참조.

**보강 범위 기본값**: `empty` tier 는 항상 후보. `shallow` tier(이미 문단이 있는 intake
이슈 등)는 사용자가 "전부 깊게" 를 원할 때만 포함 — 기본은 표에 회색으로 보이되 선택 해제
상태로 두고 사용자가 켜게 한다. 멀쩡한 문단을 무더기로 갈아엎지 않기 위함.

### Step 3a — 그룹핑 매핑

각 고아 이슈를 **가장 맞는 기존 프로젝트**에 매핑한다. 추측이 아니라 근거로:

- 이슈 제목/본문 키워드를 프로젝트의 `summary`/`description` 에 적힌 도메인·경로와 대조.
- **유사 이슈 분포 근거 병용** — `linear-register/references/dedup-grouping.md` §3
  (그루핑 SSOT, register 와 공유): 이 이슈와 유사한 기존 이슈들이 이미 속한
  project·라벨 분포를 배치 근거로 쓰고, 근거 이슈 ID 를 표에 병기한다.
- 모호하면 코드그래프(`semantic_search_nodes`)로 이슈가 가리키는 실제 모듈을 찾아 그
  모듈이 속한 도메인의 프로젝트로 보낸다.
- **어디에도 안 맞으면** 새 프로젝트를 *제안*한다(자동 생성 금지) — 이름·summary 초안을
  표에 넣고, 같은 갭의 다른 이슈도 묶어 묶음을 정당화한다(이슈 1개용 새 프로젝트는 과투자).

### Step 3a-2 — 배치 재검토 (이미 프로젝트/마일스톤이 붙은 이슈)

고아만 보고 끝내지 않는다 — **이미 project 가 붙은 open 이슈**(Step 2 행의
`project != null`)도 배치 적합성을 검토한다. 판단 기준은 Step 3a 와 동일(제목/본문 ↔
프로젝트 summary/description 대조 + 유사 이슈 분포 근거). 스코프 게이트:

- **평시 groom** — *명백한* 오배치만 재배치 제안한다(이슈 내용이 그 프로젝트 도메인과
  정면으로 어긋나는 경우). 애매한 경계 케이스는 건드리지 않는다 — 근거 약한 재배치
  남발은 churn 이고 surgical 위반이다.
- **사용자가 "재정리/재배치/전면 정리"를 명시** — 배정된 이슈 전수를 재검토하고,
  경계 케이스도 근거와 함께 표에 올려 사용자가 고르게 한다.

**마일스톤 정합(재배치의 동반 처리).** milestone 은 project 소속이다 — 이슈를 다른
프로젝트로 옮기면 기존 milestone 소속은 무효가 된다:

- 재배치 행마다 milestone 조치를 **함께 명시**한다: 새 프로젝트에 대응 milestone 이
  있으면(`list_milestones {새 project}` 로 확인) 그리로 이동, 없으면 **해제가 기본**
  (해제만 하고 신규 milestone 을 조용히 만들지 않는다 — 체인 기반 milestone 설계는
  linear-prioritize Step 6 의 일).
- 프로젝트는 그대로인데 **milestone 만 어긋난** 이슈(무관 milestone 에 편입 등)도 같은
  표에서 해제/이동을 제안할 수 있다 — 단 이것도 명백한 경우만(평시 스코프 게이트 동일).

Step 1 전수를 훑으며 **서로 사실상 같은 작업**인 OPEN 이슈 쌍을 찾는다(모델 판단 —
register 의 신규↔기존 dedup 과 달리 여기는 기존↔기존). 발견하면 자동 처리하지 말고
Step 4 표에 별도 블록으로 제안한다: 남길 이슈(더 충실한 쪽) + 접을 이슈 +
처리 방식(`duplicateOf` 마킹 권장 / 내용 상호보완이면 한쪽 병합 후 duplicateOf).
확신 없는 쌍은 `relatedTo` 제안으로 낮춘다 — 오탐으로 이슈를 접는 비용이 크다.

### Step 3b — 설명 보강

`references/enrichment-template.md` 를 읽고 그 템플릿·근거수집 순서·tier별 깊이를 따른다.
요지: 코드그래프→메모리→grep 순으로 근거를 모아 `## 작업 내용 / ## 수용 기준 / ## 추천`
(+ 경계 있으면 `## 범위 밖`) 을 register 화이트리스트·600자 계약대로 채우고, 원본은
**이슈 코멘트로 먼저 이관**한 뒤 본문을 교체한다. 못 본 건 단언 금지.

**추천 + 체인(보강 대상에만).** 보강하는 이슈에는 `## 추천`(적응형 도구 추천)을 함께 넣는다 —
규칙은 `~/.claude/skills/linear-register/references/recommend-section.md` §A(SSOT, linear-register
와 공유). Step 1 에서 읽은 관계(`blockedBy`/`blocks`/`parent`)로 **연결된** 이슈면 §B 의
`## 다음 작업`(전방 포인터 + kickoff 프롬프트)도 추가한다. **healthy 이슈엔 붙이지 않는다** —
보강 대상(empty/shallow)에만. surgical 불변식 보존.

### Step 3d — 프로젝트 위생 (완료·빈 프로젝트 정리)

이슈만 보고 끝내지 않는다 — Step 1 의 `list_projects` + 이슈 전수로 **프로젝트
라이프사이클 정합**도 검토한다. 프로젝트별 open 이슈 수를 대조해:

- **완료 후보** — open 이슈 0 + 소속 이슈 전부 Done: 상태가 아직 진행형이면
  `완료 전이` 제안(`save_project {id, state}` — state 값은 하드코딩하지 말고 실제
  워크스페이스의 프로젝트 상태 어휘를 확인해 쓴다).
- **빈 프로젝트** — 소속 이슈 자체가 0: 정리(완료/취소 전이) 제안. 단 최근 생성
  (신규 계획용일 수 있음)이면 `유지` 로 두고 사유 명기.
- **삭제는 제안하지 않는다** — Linear MCP 에 프로젝트 삭제 도구가 없다. 필요하면
  상태 전이까지만 하고 수동 삭제를 안내한다.
- **open 이슈가 하나라도 남은 프로젝트는 완료 전이 금지** — 위생은 사실 정합이지
  강제 마감이 아니다.

평시 groom 에선 명백한 것만(전부 Done·완전 빈 것). 애매하면 표에 올리되 `유지` 기본.

### Step 4 — 제안 표 + 승인 게이트

바꿀 전부를 **하나의 표**로 보인다. 두 블록:

```
## 그룹핑 (N건)
| 이슈 | 현재 | → 프로젝트 | 근거 |
|---|---|---|---|
| ADT-7 에셋 벌크업로드 | (없음) | Admin·페르소나 에디터 | 에셋 업로드 = admin 도메인 |
| ADT-8 N개 영역 선택 | (없음) | 지도·분석 | 탐색탭 격자선택 = map/panels |

### 재배치 (있으면 — Step 3a-2)
| 이슈 | 현재 project · milestone | → project · milestone 조치 | 근거 |
|---|---|---|---|
| ADT-19 결제 웹훅 재시도 | 지도·분석 · M2 | Billing · milestone 해제 | 웹훅=billing 도메인, 새 프로젝트에 대응 M 없음 |

### 새 프로젝트 제안 (있으면)
| 이름 | summary | 묶을 이슈 |
|---|---|---|

### 중복 제안 (있으면 — Step 3c)
| 남김 | 접음 | 방식 | 근거 |
|---|---|---|---|
| ADT-12 | ADT-31 | duplicateOf | 같은 rollup 인덱스 작업, ADT-12 가 AC 보유 |

### 프로젝트 위생 (있으면 — Step 3d)
| 프로젝트 | 현재 state · open/전체 | 조치 | 근거 |
|---|---|---|---|
| 온보딩 개편 | started · 0/7 | 완료 전이 | 소속 7건 전부 Done |
| (구)실험용 | planned · 0/0 | 유지 | 빈 프로젝트지만 최근 생성 — 확인 필요 |

## 보강 (M건)
| 이슈 | tier | 보강 요지 (작업 내용/수용 기준/추천 한 줄, 경계 있으면 범위 밖, 연결되면 다음 작업) |
|---|---|---|
| ADT-7 | empty | 벌크업로드 UI=AssetUploader, 다중 select+큐, Acc=N개 동시업로드, 추천=직접구현 |
```

**어디에도 안 붙는 이슈**(맞는 프로젝트 없음 + 신설 정당화 부족)는 표에서 빼지 말고
`미배정 유지` 행으로 사유와 함께 남긴다 — 조용히 빠지면 사용자는 그루밍이 커버했다고 믿는다.

**scan-only 면 여기서 갈라진다** — 승인 문구 없이 이 표를 리포트 이슈에 코멘트로 게시하고
종료한다(`references/scan-only.md`). 아래 승인·반영은 interactive 모드 전용.

그다음 "이대로 그룹핑 N건 + 보강 M건을 반영할까요? (제외할 항목 알려주세요)" 로 동의를
받는다. 사용자가 일부만 고르면 그것만. **승인 전 어떤 write 도 하지 않는다.**

**승인 신호 판독** — "ㅇㅇ"·"해줘"·"진행"·"반영해" 같은 짧은 긍정도 포괄 승인이다. 되묻지
말고 바로 Step 5 를 실행한다(재확인 반복은 게이트가 아니라 마찰이다). 제외 항목만 말하면
나머지 전체 승인으로 읽는다. 승인인지 추가 논의인지 정말 모호할 때만 **1회** 확인하고,
그때도 "무엇을 실행할지"를 한 줄로 재진술해 답을 쉽게 만든다.

### Step 5 — 일괄 반영

승인된 것만, 순서대로:

1. **새 프로젝트 먼저** — `save_project {name, summary, description, addTeams:[team]}`. 반환
   id 를 받아 그 프로젝트로 갈 이슈 배정에 쓴다.
2. **그룹핑** — `save_issue {id, project}`. project 는 **가능하면 id**(1번 반환값 또는
   `list_projects` 로 확인한 id)로 넘긴다 — 이름 문자열은 동명 프로젝트·오탈자·타팀 동명이
   있으면 엉뚱한 곳에 붙거나 조용히 무시된다. 프로젝트 배정과 함께 라벨이
   비어 있으면 동반 부착하되, **팀 라벨셋 실측 어휘 내에서만**
   (`linear-register/references/dedup-grouping.md` §1.5 — `list_issue_labels` 선행,
   `area:*` 는 보유 팀만, 없는 라벨명 부착 금지). 그 외 필드는 안 건드린다.
2.2. **재배치** — 승인된 재배치 행은 `save_issue {id, project:<새 id>, milestone:<승인된
   조치>}` 한 번에 처리한다. milestone 조치는 표에 명시된 대로: 이동이면 새 프로젝트의
   milestoneId, 해제면 null 을 **명시적으로** 넘긴다 — 구 project 의 milestone 이 이동
   후 자동 무효화된다고 신뢰하지 않는다(Step 6 재조회로 실제 해제 확인). 본문
   (description)은 건드리지 않는다.
2.5. **중복 반영** — 승인된 중복 쌍만 `save_issue {id, duplicateOf}` (또는 relatedTo).
   접는 이슈의 본문에 보완할 내용이 있으면 남기는 이슈에 먼저 병합한 뒤 마킹.
3. **보강** — 원본이 아직 본문에만 있으면 **먼저** `save_comment {issue, body:<원본 전문>}`
   로 이관하고(실패 시 그 이슈 보강 중단 — 순서 불변식), **그다음** `save_issue {id,
   description}` 에 새 계약대로 쓴 본문을 넣는다. 같은 이슈가 그룹핑+보강 둘 다면 한 번의
   `save_issue` 로 `project`+`description`(+라벨) 함께 넣는다.
4. **프로젝트 위생** — 승인된 완료/정리 행만 `save_project {id, state:<승인된 상태>}`.
   description·이슈는 건드리지 않는다 — 상태 필드만.

**병렬화 가드**: **의존 없는 독립 write**(순수 project 배정·라벨 부착, 관계 무관)만
Workflow fan-out 으로 병렬 가능. **관계 세팅(blocks/blockedBy/parent)이 걸린 write 는 순차** —
관계는 대상 이슈가 먼저 존재·확정돼야 하므로 병렬화하면 순서 의존이 깨진다. 새 프로젝트
생성(1번)은 항상 그룹핑(2번)보다 선행(id 의존).

각 write 후 성공/URL 을 요약 보고. 실패(권한/네트워크)는 그 이슈만 건너뛰고 계속 — 한
건 실패가 전체를 멈추지 않게(나머지는 완수, 실패분만 따로 보고).

### Step 6 — 반영 검증 + 최종 보고 (건너뛰지 않는다)

write 를 다 친 뒤 **대상 이슈를 다시 읽어** 의도한 필드가 실제로 그렇게 됐는지 확인한다.
싸게 하는 법: `list_issues {team, project:<새 project id>}` 한 번으로 그 프로젝트에 실제로
들어간 이슈 목록을 받아 승인 목록과 대조(개별 `get_issue` 는 어긋난 건만). 보강은 반환된
description 길이·헤딩 존재로 확인.

그다음 결과를 표로 닫는다 — 검증된 것만 ✅ 다:

```
| 이슈 | 조치 | 결과 |
|---|---|---|
| SSO-62 | → 프로젝트 X | ✅ 재조회 확인 |
| SSO-64 | → 프로젝트 X | ⚠️ project 필드 비어 있음 — 재시도/원인 |
| SSO-67 | 미배정 유지 | — (사유: 맞는 프로젝트 없음) |
```

어긋난 건은 한 번 재시도하고, 그래도 안 되면 무엇이 왜 안 됐는지 그대로 보고한다. 조용히
성공으로 뭉개면 사용자는 반영됐다고 믿고 다음 작업을 그 위에 쌓는다.

## Anti-patterns

- 승인 없이 `save_issue`/`save_project` 호출 — 외부 write 는 항상 표→동의 뒤(Step 4).
- 승인을 받고도 표까지만 내고 종료 — 반영 0건. 게이트는 종료점이 아니다(Step 5 필수).
- 승인 뒤 "정말 진행할까요?" 재확인 반복 — 게이트 1개면 충분, 나머지는 마찰.
- `save_issue` 무에러 = 반영으로 단정 — 재조회 없이 ✅ 보고 금지(Step 6).
- 어디에도 못 붙인 이슈를 보고에서 누락 — `미배정 유지` 로 명시.
- 보강하며 원본 스크린샷/문장 삭제 — 본문 교체 **전에** 코멘트로 이관한다(순서 뒤집기 금지).
- 레거시 헤딩 이슈를 "구조 없음"으로 보고 전수 재작성 — 레거시도 healthy 다(소급 수정 금지).
- Done/Canceled 이슈 그루밍 — OPEN 만(스크립트가 `skippedClosed` 로 분리).
- 이미 구조 있는 이슈를 다시 갈아엎기 — healthy 는 손대지 않음(배치 재검토와 별개 —
  재배치는 배치 필드만, 본문 불가침).
- 근거 약한 재배치 남발 — 평시엔 명백한 오배치만, 전수 재검토는 명시 요청 시(Step 3a-2).
- 프로젝트만 옮기고 stale milestone 방치 — 재배치 행은 milestone 조치 명시 필수.
- 재배치하며 신규 milestone 조용히 생성 — 체인 milestone 설계는 linear-prioritize 의 일.
- 이슈 1건 때문에 새 프로젝트 생성 — 기존에 맞추거나, 새 프로젝트는 여러 이슈를 묶을 때만.
- open 이슈 남은 프로젝트를 완료 전이 — 위생은 사실 정합이지 강제 마감 아님(Step 3d).
- 프로젝트 삭제 시도 — MCP 에 삭제 도구 없음. 상태 전이까지만, 삭제는 수동 안내.
- 도구 이름·파일 경로 추측 단언 — available tools / 코드그래프 / Read 로 확인 후.
- scan-only 에서 `save_issue`/`save_project` 호출 — 승인자 없는 반영(리포트 코멘트만 허용).
- 프롬프트에 `scan-only` 가 없는데 스스로 scan-only 로 내려가 반영을 건너뜀 — 사용자는
  그루밍이 반영된 줄 안다. 모드 진입은 명시적일 때만.
