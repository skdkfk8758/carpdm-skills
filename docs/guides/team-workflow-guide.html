02핵심 개념 — 스킬보다 먼저

Skill-first

비trivial 코드 작업(3+ 파일 · 200+ LOC · 검증 루프)은 즉흥 편집 대신 스킬 경유. 오타·1-2 파일은 그냥 직접.

승인 게이트

외부 write(이슈 생성·PR 머지·삭제)는 스킬이 미리보기를 먼저 보여주고 승인을 기다린다. 스킬 발동 자체는 항상 안전.

Worktree 격리

새 브랜치 작업은 예외 없이 worktree 로. 메인 체크아웃은 항상 trunk — uncommitted 노출을 최소로.

자동 가드(훅)

보호 브랜치 차단 · 파괴 명령 경고 · push/PR 전 CI 3종 로컬 선실행. 훅이 막으면 우회하지 말고 메시지를 따를 것.

모드 2종

caveman(산문 압축) · ponytail(코드 YAGNI 사다리, 매 세션 자동 full). /ponytail lite|ultra 로 조절.

codex 교차모델

이슈등록 실행 · 착수 재플래닝 · plan 비평자가 codex exec 로 다른 모델의 판단을 산다. codex 없으면 자동 폴백.

04시나리오 플레이북 — 작업 유형별 워크플로우

개발에서 실제로 마주치는 작업 유형 8가지. 각 탭이 그 시나리오의 단계·스킬·주의점을 담는다. 점선 원은 조건부 단계 — 해당 없으면 건너뛴다.

🔨 기능 구현 — 없던 것을 새로 만든다

핵심 스킬 /forge. 요구가 crisp 하면 forge 직행, 크거나 흐릿하면 상류(인터뷰→플랜→이슈)를 거친다.

?
아이디어가 흐릿하면 — /deep-interview

라운드당 한 질문 인터뷰로 REQ spec 결정화. 이미 명확하면 스킵.

?
크거나 위험하면 — /deep-plan

PLAN + UI 시안 + Goal Prompt 산출(codex 비평자 debate). 구현은 안 함.

?
설계 질문이 대화로 안 풀리면 — /prototype · /design-an-interface

상태 모델·로직이 맞는지 throwaway 코드로 답하거나, 모듈 인터페이스 시안을 병렬로 여러 개 떠서 비교.

?
한 세션에 안 담기는 초대형 안개 작업이면 — /wayfinder

decision ticket 맵으로 결정을 하나씩 해소해 길을 낸 뒤, plan→분할로 합류.

?
여러 세션짜리면 — /linear-register 분할

plan 을 vertical slice 이슈 트리로. 미리보기 승인 후 codex 가 등록.

1
구현 — /forge (직접) 또는 /linear-goal (자율)

forge: 소크라테스 인터뷰 → plan 게이트 → 동적 워크플로 TDD → 보안 검증. goal: worktree + worker + PR 까지 자율.

2
머지 — /land

CI green 확인 → squash 머지 → master pull → 브랜치 정리 → Linear Done 전이.

주의
  • UI 가 낀 기능이면 시안 선행 — /mockup 으로 화면을 먼저 승인받고 구현에 들어간다.
  • 작업은 worktree 에서 — 브랜치명에 이슈 ID 를 박아야 PR↔Linear 자동연동이 걸린다.
  • 소형 기능(1-2 파일)은 이슈·플랜 없이 forge 만으로 충분 — 상류를 의무로 만들지 말 것.

♻️ 기능 수정·개편 — 동작을 의도적으로 바꾼다

핵심 스킬 /renew. "고장나서 고침"(hunt)과 다르다 — 멀쩡히 돌아가는 것을 다른 동작으로 바꾸는 작업.

1
/renew 발동 — 바뀔 것 vs 보존할 것 분리

인터뷰가 "무엇이 바뀌고, 무엇은 절대 깨지면 안 되는지"(하위호환·기존 호출자)를 먼저 못 박는다.

?
전면 개편이면 — /deep-plan 선행

화면·플로우 전체를 갈아엎는 규모면 플랜+시안으로 방향을 먼저 확정.

2
TDD 구현 — 보존 동작은 회귀 테스트로 잠금

바뀌는 동작은 새 테스트, 보존 동작은 기존 테스트 green 유지가 성공 기준.

3
/land 머지

수용 기준 100% 체크 후에만 — 미검증 항목 남기고 Done 금지.

경계 판정
  • "예전엔 됐는데 안 돼" → hunt(버그). "이제부터 다르게 동작해야 해" → renew.
  • 마이그레이션·API 계약 변경이 끼면 DB 탭의 slow-lane 규율이 함께 적용된다.

🐛 버그픽스 — 재현 먼저, 회귀 잠금

핵심 스킬 /hunt. 재현 없는 수정은 수정이 아니다 — 실패하는 테스트를 먼저 만들고 그것을 green 으로.

1
/hunt 발동 — 재현·근본 원인 인터뷰

정확한 재현 조건(입력·환경·타이밍)과 기대 동작을 먼저 고정. 추측 수정 금지.

?
원인이 안 잡히면 — /diagnosing-bugs 진단 루프

간헐 flake·회귀 구간 미상 같은 어려운 버그는 "이 버그에서 red 가 되는 명령 하나"를 먼저 확보하는 진단 스킬로.

2
실패 테스트 먼저 → 수정 → green

회귀 테스트가 잠금 장치 — 같은 버그가 다시 오면 CI 가 잡는다.

3
/land 머지

연결 이슈가 있으면 Done 전이까지.

주의
  • 재현 검증이 운영 DB·실데이터를 건드리면 비가역 — 반드시 격리 환경에서.
  • 증상만 덮는 수정(try-catch 로 감싸기 류)은 hunt 인터뷰가 걸러낸다 — 근본 원인까지.
  • 보안성 버그(authz 우회·주입)면 머지 전 /security-review 를 직교 게이트로.

🧹 리팩토링 — 동작 불변, 구조 개선

성공 기준이 명확하다: 리팩터 전후 테스트 전부 green. 발굴(무엇을)과 적용(어떻게)을 나눠 쓴다.

1
후보 발굴 — /ponytail-audit · /clean-architecture · /improve-codebase-architecture

과잉설계 삭제 후보 랭킹(ponytail) · 의존성/레이어 경계 위반(clean-architecture) · deepening 기회 스캔+HTML 리포트(improve). 셋 다 리포트만, 안 고침.

2
소형 적용 — /simplify

변경분 대상 단순화 리뷰 + 수정 적용까지 한 번에. diff 스코프의 정리엔 이게 가장 빠르다.

?
대형 구조 개편이면 — /renew

모듈 경계·인터페이스를 바꾸는 규모면 renew 파이프라인으로 — 보존 동작을 테스트로 잠그고 진행.

3
검증 — 전후 테스트 green + /code-review

동작 불변 주장은 테스트가 증명한다. diff correctness 리뷰로 마감.

규율
  • 안 깨진 것을 요청 없이 리팩터하지 않는다 — 범위는 항상 명시 요청에 연결(surgical).
  • 기능 전환 시 옛 경로는 같은 커밋에서 삭제 — "다음 PR 에서 정리" 금지(YAGNI).
  • 테스트가 없어 동작 불변을 증명할 수 없으면, 리팩터 전에 특성 테스트부터(/tdd).

🗄 DB 스키마 변경 — 코드보다 느린 레인

코드는 자주 머지해도 운영 DB apply 는 별도 단계다(slow-lane). 현황 파악 → 설계 → 구현 → 검증 순.

1
현황 파악 — /erd

라이브 DB 읽기 전용 introspect 로 현재 스키마·관계·적재량을 그림으로. 변경 설계의 출발점.

?
스키마가 plan 핵심이면 — /deep-plan (ERD companion)

plan 과 함께 변경 후 스키마의 -erd.html 시안이 같이 나온다.

2
구현 — /renew 또는 /forge

마이그레이션은 타임스탬프 prefix(YYYYMMDDHHMMSS_slug) — 병렬 브랜치 충돌 구조적 제거.

3
운영 apply — slow-lane

자동 migrate:up 지양, 개별 apply 후 information_schema 실조회로 검증. "실행됨 ≠ 적용됨".

파괴 방향 주의
  • 테이블·대량 데이터 삭제 직전엔 liveness 3증거(커넥션·write·참조 grep) 선행 — "죽었다"는 설명을 믿지 않는다.
  • 검증 쿼리의 LIKE '..._...' 언더스코어는 와일드카드 — 이스케이프 또는 = 완전일치.

🎨 UI 작업 — 시안 먼저, 사람 눈으로 마감

코드보다 시안이 먼저다 — 승인된 그림이 구현 계약이 된다. 마지막 검증은 자동화가 아니라 사람의 눈.

1
시안 — /mockup (기존 룩 충실) · /imprint (DESIGN.md 재현) · frontend-design (자유 창작)

self-contained HTML 시안이 Artifact URL 로 배포돼 링크로 리뷰. 프로젝트 토큰에서 벗어나지 않는다.

2
구현 — /forge (새 화면) 또는 /renew (기존 화면 개편)

승인된 시안이 Phase 1 입력으로 들어간다.

3
사람 확인 — dev-server-daemon

"서버 올려둬, 내가 확인할게" — 세션이 끝나도 살아있는 daemon 으로 띄우고, 실측 포트로 안내받는다.

4
/land 머지

[HUMAN] 시각 확인 항목이 남았으면 체크리스트로 인계 — 위장 완료 금지.

주의
  • 시안 갱신은 같은 파일 경로로 재배포 — URL 이 유지돼 이전 링크가 최신을 가리킨다.
  • 포트는 추정 금지 — :3000 은 대개 다른 프로젝트가 물고 있다. daemon 이 실측으로 찍은 포트만.

🎫 티켓 자율 처리 — Linear 이슈를 맡긴다

잘 쓰인 이슈는 에이전트가 혼자 끝까지 간다. 이슈 품질이 자율 실행 품질이다.

?
뭐부터 할지 모르면 — /linear-prioritize

미완 이슈 전체를 의존·병렬 분석해 우선순위와 병렬 가능 트랙을 뽑는다.

?
결정 갈래가 많으면 — /linear-replan

착수 직전 codex 초안 + 갈래 인터뷰로 착수 계획을 확정, 이슈 코멘트로 남긴다.

1
/linear-goal — 자율 실행

이슈의 작업 내용·수용 기준을 Goal Prompt 로 매핑 → 확인 게이트 → worktree 에서 goal worker 가 구현·검증 → PR + In Review.

2
/land — 머지 + Done 전이

수용 기준 체크박스가 100% 인지 스캔 후 Done — 미체크가 있으면 In Review 로 남기고 플래그.

주의
  • oversized 이슈(estimate≥5·cross-cutting·전면개편)는 linear-goal 이 스스로 멈추고 deep-plan+linear-register 분할을 권한다 — 억지로 밀지 말 것.
  • 수용 기준의 [AUTO]/[HUMAN] 마커가 자율/사람 검증을 가른다 — 이슈 등록 때부터 지켜진 규격.

🚀 배포 준비 — 판정 먼저, 배선은 스캐폴드로

배포 가능한가(판정)와 배포되게 만드는가(파이프라인)를 나눠 처리한다. 판정 스킬은 코드를 안 고친다 — 발견은 빌드 스킬로 라우팅.

1
/preflight — 10차원 종합 판정

코드건강·런타임·UX·확장성·기술부채까지 보고 GO / 조건부GO / NO-GO. 반드시수정(blocker)이 나오면 hunt/renew 로 수정 후 재판정.

2
/fortify — 보안 한 축 심화

앱·인증·데이터·인프라·로깅 5카테고리, 읽기전용 라이브 probe(헤더·TLS·audit) 포함. 확인필요 항목은 사람에게 정직하게 넘긴다.

?
파이프라인이 없으면 — /cicd-scaffold

develop→dev 자동, 태그→prod, ECR+self-hosted runner 형상의 GitHub Actions 를 생성.

3
/land → 릴리스

trunk 머지 후 릴리스 라인은 태그가 게이트 — 버전 태그 push 가 prod 배포를 트리거.

주의
  • 기능 수용 기준 green ≠ 보안 통과 — 보안은 직교 게이트다. 섞으면 둘 다 샌다.
  • 인프라 항목(방화벽·백업 복구 테스트)은 코드 밖 — 추측 PASS 금지, "확인필요"로 사람에게.

05스킬 사용 가이드 — 그룹별

07이 레포를 유지보수할 때

스킬을 고치는 사람의 루프 — live 가 SSOT, repo 는 배포 미러.

# live ~/.claude/skills/<name>/ 편집 후
bash sync.sh        # 스킬 + 글로벌 덤프 미러 (secret 마스킹·스캔 게이트 내장)
/ship               # PR → CI 대기 → 승인 1회 → squash 머지 → 로컬 재동기화
push/PR 순간마다 CI 3종(frontmatter · invisible-chars · README 카탈로그)이 로컬에서 먼저 돈다 — 로컬 green = CI green. 루트 메타(README·scripts)는 ship 범위 밖이라 수동 커밋 후 /land. MCP·플러그인을 새로 깔았으면 global/setup/replicate.sh 목록도 같이 갱신할 것 — 안 하면 다음 팀원 온보딩에서 빠진다.
carpdm-skills · 스킬 인벤토리 SSOT 는 각 skills/<name>/SKILL.md · 아키텍처 결정은 rules/project.md · 글로벌 덤프 구조는 global/README.md · 마크다운 판: docs/guides/team-workflow-guide.md
