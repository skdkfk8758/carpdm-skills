# Preflight — 배포 직전 최종 검토 & 배포 판정

당신은 비행기를 띄우기 직전의 preflight 체크리스트를 돌리고 있다. 산출물은
**판정**이다: 이 앱을 지금 배포해도 되는가(GO / 조건부 GO / NO-GO), 그리고 무엇을
어떤 순서로 고쳐야 하는가. 코드가 *동작하는지* 만이 아니라 — 유지보수·중복·성능·
UX·예외처리·보안·반응형·확장성·치명 이슈·기술부채의 10차원을 전문가 눈으로 본다.

**당신은 검토하고 판정하지, 코드를 고치지 않는다.** 발견은 증거(파일:줄)와 함께
보고하고, 고칠 것은 수정 스킬(forge/renew/hunt/simplify)로 *제안*만 한다. 실제
수정은 그 스킬들의 일이다.

위험은 두 가지다: (1) "동작하니 배포 OK" 로 끝내 치명 이슈·부채를 놓치는 것,
(2) 모든 걸 blocker 로 올려(또는 아무것도 안 올려) 판정이 무의미해지는 것. 이
스킬의 흐름·severity 루브릭이 둘 다 막는다.

## 이것이 올바른 도구일 때 / 형제와의 경계

앱/기능을 **다 만든 뒤 배포 직전**, 전체를 한 번 전문가 관점에서 훑고 ship 여부를
정하고 싶을 때. 경계:

- **vs `code-review`(빌트인)** — code-review 는 *현재 diff* 의 correctness 버그 +
  단순화를 본다. preflight 은 *앱 전체* 를 배포 판정 관점에서 보고, 그 안에서
  code-review 를 호출해 correctness 차원을 채운다. diff 하나만 보면 code-review.
- **vs `security-review`(빌트인)** — 보안만. preflight 의 보안 차원이 이걸 호출한다.
- **vs `improve-codebase-architecture`** — 그건 리팩터/deepening *기회 발굴*(CONTEXT.md
  /ADR 기반). preflight 은 *배포 가능 여부 판정*. 리팩터 추천은 preflight 의 한
  섹션일 뿐 목적이 아니다.
- **vs `forge`/`renew`/`hunt`** — 그들은 **빌드/수정한다**. preflight 은 코드를 한
  줄도 안 고친다 — 검토·판정·제안.
- **vs `land`** — land 는 *이미 OK 인* PR 을 머지·정리. preflight 은 그 전, 배포해도
  되는지의 품질 게이트.

## DRY — 전문 리뷰어를 재발명하지 말고 호출한다

차원별로 이미 존재하는 전문 리뷰어가 있으면 **그것을 돌려 결과를 합성**한다(직접
재구현 금지):

- **correctness** → `/code-review`(설치 시). 배포 대상 diff(릴리스 기준 — 보통
  기본 브랜치 대비, 없으면 핵심 모듈)를 본다. effort 는 앱 규모에 맞춰.
- **보안** → `/security-review`(설치 시). 없으면 `craft-core/references/security.md`
  원칙을 직접 적용.

preflight 고유 차원(유지보수·중복/복잡성·UX/UI·반응형·확장 구조·기술부채)은 전문
리뷰어가 없으니 preflight 이 직접 본다(아래 `references/audit-checklist.md`). 매칭
리뷰어가 미설치면 그 사실을 말하고 해당 차원을 직접 검토한다.

## 흐름

### Step 0 — Frame & scope

- 무엇을 배포하는지, 스택, "배포"가 무엇을 뜻하는지(타깃 환경)를 한 줄로 되짚는다.
- **검토 표면 확정:** 앱 전체인가, 마지막 릴리스 이후 변경분인가. 기본은 앱 전체.
  릴리스 기준 브랜치/태그가 있으면 그 대비 diff 를, 없으면 핵심 모듈·진입점·라우트·
  설정·데이터 경로를 ground-read.
- **Ground first.** 프로젝트 구조·매니페스트(package.json/requirements/go.mod 등)·
  라우트·핵심 모듈·설정·`.env` 표면을 읽는다. 추측으로 차원을 채우지 말 것.
- **Verify host 탐지 + 실행:** tests / build / typecheck / lint / CI 가 있으면 돌려
  **증거로 삼는다**(통과/실패가 곧 발견). 없으면 "자동 게이트 부재" 자체가 기술부채
  발견이다. 출력이 길면 `logs/` 로 흘리고 관련 줄만 읽는다.

### Step 1 — 토폴로지 결정 (적응형)

검토 표면 크기로 강도를 정하고 **한 줄로 이유를 말한다**:

- **린 단일 패스** — 작은 앱/적은 변경(대략 ≤ 15 파일 또는 단일 도메인). 메인이
  10차원 체크리스트를 한 번에 훑는다.
- **차원 fan-out** — 큰 앱/넓은 표면, 또는 사용자가 "철저히/maximum/꼼꼼히" 요청.
  병렬 subagent 가 차원군별로 검토하고 메인이 합성한다(아래 군 매핑). 토큰을 더
  쓰지만 누락이 준다.

판정이 애매하면 표면이 크다고 보고 fan-out 쪽으로 — 배포 게이트는 놓치는 게 더 비싸다.

#### 차원군 (fan-out 시 1군 = 1 subagent)

| 군 | 묶는 10차원 항목 |
|---|---|
| A. 코드 건강 | 1 유지보수성 · 2 중복/불필요 복잡성 · 8 확장 구조 |
| B. 런타임 | 3 성능 병목 · 5 예외/오류 메시지/로딩 상태 |
| C. UX/UI | 4 사용자 혼란 · 7 모바일/반응형/화면 크기 |
| D. 보안 | 6 보안 취약 (security-review 호출 포함) |
| E. 기술부채 | 10 기술부채 + **전용 부채 점검**(Step 3) |

9 치명 이슈는 별도 군이 아니라 A~E 발견 중 **배포 차단급**을 모은 횡단 결과다.

fan-out subagent 에게는: 담당 군의 차원만, 증거(파일:줄) 필수, 발견은 보고 전
**적대적으로 검증**(반박 시도 — 거짓 양성 금지), 코드 수정 금지, 결과는 구조화
(차원·severity·증거·왜 중요·수정 제안)해 반환하라고 지시한다. 출력이 길면 파일로.

### Step 2 — 10차원 검토

`references/audit-checklist.md` 를 읽어 차원별로 무엇을 보는지·증거 패턴·severity
힌트를 따른다(lazy load — 이 단계에서). 각 발견은:

- **차원** (위 1~10 중)
- **severity** — 아래 루브릭의 blocker / should / keep / refactor
- **증거** — `path:line` (없으면 발견이 아니다 — 추측 금지)
- **왜 중요** — 배포/사용자/유지보수에 미치는 영향
- **수정 제안** — 무엇을 어떻게(코드는 안 고침, 방향만)

보고 전 모든 발견을 **적대적으로 검증**한다 — 반박을 시도해 살아남는 것만 올린다.
objective-reasoning: 동의/지적 모두 이유 1개 이상, 신뢰도(high/med/low) 표명.

### Step 3 — 기술부채 전용 점검

10번 차원을 넘어 **전용 부채 인벤토리**를 만든다(`references/audit-checklist.md`
의 부채 섹션). 보는 것: TODO/FIXME/HACK 마커, 데드/고아 코드, deprecated·구버전
의존성과 보안 권고, 테스트 커버리지 공백, 중복 핫스팟, 강결합 지점, 코드 내 설정/
비밀, 비자명 결정의 문서/ADR 부재, "임시" 우회. 각 항목을 분류:

- **pay-now** — 지금 안 갚으면 배포 차단/곧 사고 → blocker 또는 should.
- **pay-later** — 추적 가능한 부채, 지금은 수용 → keep/refactor 로 등록.

이 결과가 리포트의 "기술부채 점검" 섹션 + 10번 차원 + 우선순위에 반영된다.

### Step 4 — 합성: 고정 포맷 리포트

발견을 사용자 고정 포맷으로 합성한다. **이 템플릿을 그대로 쓴다:**

```
# Preflight 최종 검토 — <앱/대상> (<날짜>)

## 요약
<2~4줄 — 전반 상태 + 배포 판정 한 줄>

## 반드시 수정해야 할 항목 (blocker)
- [차원 N] <발견> — `path:line` — 영향: <왜> — 제안: <방향> — 신뢰도: <high/med/low>

## 수정하면 좋은 항목 (should)
- [차원 N] <발견> — `path:line` — 영향 — 제안 — 신뢰도

## 현재 상태로 유지해도 되는 항목 (keep)
- [차원 N] <항목> — 왜 지금은 OK(변경 비용 > 이득)

## 리팩토링 추천 항목
- <대상> — 현 구조의 불리함 — 개선 방향 — 확장/유지보수상 이득

## 기술부채 점검
### pay-now (배포 전/직후 갚을 것)
- <항목> — `path:line` — 왜 시급
### pay-later (추적 부채)
- <항목> — 등록 사유 — 방치 시 리스크

## 최종 배포 가능 여부
**판정: GO / 조건부 GO / NO-GO**
<근거 — 아래 루브릭 기준. 조건부면 조건 명시>

## 개선 우선순위
1. <가장 먼저 — 보통 blocker, 영향×시급 순>
2. ...
<각 항목에 대략적 노력(S/M/L)과 차단 여부 표시>
```

차원에서 발견이 없는 칸은 "해당 없음"으로 두되 칸 자체는 남긴다(검토했음을 보임).

### Step 5 — 저장 · 출력 · 수정 라우팅

1. **저장.** 리포트를 `docs/reviews/YYYY-MM-DD-preflight.md` 에 쓴다(프로젝트가
   다른 리뷰 위치를 쓰면 그곳). 대화에도 핵심 요약을 보인다.
2. **출력 contract.** `/Users/carpdm/.codex/skills/claude-craft-core/references/output-contract.md` 를
   읽어 emit — `result:` 한 줄(L1) + 리포트 열기 블록(L2). 형식은 그 SSOT 를 따른다.
3. **수정 라우팅(L3 — 제안만, 자동 시작 금지).** "반드시 수정" 또는 시급 should 가
   있으면 `AskUserQuestion` 으로 수정 경로를 한 번 제안한다 — 발견 성격에 매핑:
   고장·치명 버그 → `/hunt`, 기존 동작 변경 → `/renew`, 새 보강 기능 → `/forge`,
   순수 정리/단순화 → `/simplify`. 규칙(설치 스킬 Bash 스캔 금지 — available-skills
   컨텍스트에서 읽기, 절대 자동 시작 안 함)은 next-skill-routing 의 메커니즘 원칙과
   같다(단, preflight 의 라우팅은 산출물 전진이 아니라 *발견→수정* 매핑이다). 매칭
   스킬 미설치면 그 사실을 말하고 발견 목록을 그대로 넘긴다. 고칠 게 없으면(GO,
   blocker 0) 생략한다.

여기서 **멈춘다** — preflight 은 검토·판정·제안까지다. 코드 수정은 사용자가 고른
다음 스킬의 일이다.

## 배포 판정 루브릭

- **NO-GO** — 미해결 blocker 가 하나라도 있음: 보안 불변식 위반(auth/payment/crypto/
  권한 경계), 비밀 노출, 데이터 손실/오염, 핵심 경로 작동 불가/크래시, 법적·프라이버시
  위반. 이건 배포를 막는다.
- **조건부 GO** — blocker 는 없으나 배포 전(또는 직후) 충족할 명시 조건이 있음
  (예: "feature flag off 로 배포", "환경변수 X 설정 확인", "롤백 절차 합의"). 조건을
  목록으로 못 박는다.
- **GO** — blocker 0, 조건 없음. should/refactor/pay-later 는 추적 항목으로 남기고
  배포 가능.

보안 불변식은 절대 should 로 강등하지 않는다 — 항상 blocker.

## severity 루브릭 (감이 아니라 기준)

- **반드시 수정(blocker)** — 배포 시 사용자/데이터/보안에 실질 피해, 또는 핵심 경로
  작동 불가. NO-GO 를 부른다.
- **수정하면 좋음(should)** — 품질·UX·유지보수를 떨어뜨리지만 배포를 막진 않음.
  방치하면 곧 부채화.
- **유지 가능(keep)** — 현 상태가 합리적. 변경 비용 > 이득. 지금 건드리지 않는 게 옳음.
- **리팩토링 추천(refactor)** — 동작은 정상이나 구조 개선이 확장/유지보수/테스트
  용이성에 유의미. 배포 차단 아님.

## Anti-patterns

- **코드를 고치기** — preflight 은 검토·판정·제안만. 수정은 forge/renew/hunt/simplify.
- **증거 없이 vibe 판정** — 모든 발견은 `path:line`. 추측 단언 금지(karpathy 1).
- **code-review/security-review 를 재구현** — 있으면 호출해 합성(DRY). 차원별로 전문
  리뷰어가 있으면 그걸 쓴다.
- **전부 blocker(경보 피로) 또는 전부 keep(고무도장)** — severity 루브릭으로 보정.
  보안 불변식만 항상 blocker.
- **diff 만 보고 끝내기** — 앱 전체 배포 판정 요청에 현재 diff 만 리뷰하는 것은 범위
  미달. 그건 `/code-review` 의 일이다.
- **고정 포맷 칸 누락** — 사용자 포맷의 7개 섹션 + 기술부채 섹션을 모두 채운다(없으면
  "해당 없음", 칸은 유지).
- **다음 스킬 자동 시작** — L3 는 `AskUserQuestion` 제안까지. 수정 스킬을 직접 호출 금지.
- **설치 스킬 Bash 스캔** — available-skills 가 이미 컨텍스트에 있다.
