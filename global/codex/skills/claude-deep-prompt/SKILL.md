# deep-prompt — 자율 실행용 Goal Prompt 저작

사용자가 "이걸 백그라운드로 돌리고 싶다"는 한두 문장을 들고 온다. 그걸 그대로
goal 칸에 넣으면 자율 에이전트는 *언제 끝났는지 모른 채* 표류한다 — 영원히 루프를
돌거나, 절반만 하고 멈추거나, 범위를 넘어 엉뚱한 걸 건드린다. 자율 실행의 실패는
거의 항상 **약한 성공 기준**에서 온다: 사람이 옆에 있으면 "이 정도면 됐어"를
판단해주지만, 백그라운드 잡에는 그 사람이 없다.

이 스킬은 흐릿한 의도를, 에이전트가 **혼자서 완료를 판정하고 루프를 빠져나올 수
있는** 고정 구조의 Goal Prompt 로 바꿔 `.md` 파일로 저장한다. 핵심 작업은 글쓰기가
아니라 **성공 기준을 측정 가능하게 못 박는 것**이다 — 나머지 섹션은 그 기준을
지지하는 받침대다.

## 이것이 올바른 도구일 때

- 사용자가 어떤 작업을 **백그라운드/자율 goal 로 돌릴** 프롬프트를 원할 때.
- 산출물이 **goal 칸에 붙여넣을 텍스트 한 덩어리**(`.md`)일 때.

손대지 말아야 할 때:

- 아이디어가 **정말로 모호하고 커서** 무엇을 만들지 자체가 안 정해졌을 때 →
  `deep-interview` 로 먼저 결정화. deep-prompt 는 *짧은* 명료화만 한다, 풀
  Socratic 인터뷰가 아니다.
- 지금 당장 **기능을 빌드/수정/디버그**할 때 → `forge`/`renew`/`hunt`. 이
  스킬은 작업을 *수행*하지 않는다; 자율 에이전트에게 줄 *지시문*을 쓴다.

## 왜 이 형태인가 — 자율성의 조건

goal 프롬프트는 사람이 지켜보지 않는 동안 에이전트가 가진 **유일한 계약**이다.
일반 대화는 막히면 사용자에게 물어보면 되지만, 백그라운드 잡은 물어볼 사람이 없는
구간을 견뎌야 한다. 그래서 세 가지가 본문에 명시적으로 박혀 있어야 한다:

1. **완료가 무엇인지** (Success Criteria) — 에이전트가 스스로 체크해 루프를 끝낼
   수 있는, 관찰 가능한 조건. 이게 약하면 자율 실행 전체가 무너진다.
2. **건드리면 안 되는 것** (Constraints) — 사람이 없으니 가드레일이 본문에
   있어야 한다. 특히 비가역·외부발신 작업의 경계.
3. **막혔을 때 어떻게 신호하는가** (Done & Report) — 끝났을 때, 또는 진짜로 막혀
   더 못 갈 때 어떻게 보고하고 빠져나오는가.

## 워크플로

순서대로. 추론으로 채울 수 있는 칸은 채우고, 자율 실행을 위태롭게 하는
빈칸만 물어라.

### 1. 입력에서 목표 추출 (있으면 안 묻는다)

사용자의 한두 문장에서 다음을 뽑아낸다. 이미 말한 건 다시 묻지 말고 확인만:

- **무엇을 달성하나** — 한 문장 동사구. ("로그인 플로우에 rate limit 추가",
  "스테이징 깨진 e2e 테스트 전부 초록으로", "이 디렉토리 문서 최신화").
- **어디서 도나** — 레포/경로/환경. brownfield 면 건드릴 영역만 가볍게
  Read/Grep 으로 확인한다(전체 레포 스캔 금지) — 근거 있는 Context·Constraints 를
  쓰기 위해서다.
- **어떻게 끝났다고 아나** — 가장 중요하고 가장 자주 비어 있는 칸. 사용자가
  완료 신호를 말하지 않았으면 여기를 물어라.

### 2. 빈칸이 자율성을 깨는지 판정 — 그럴 때만 질문

자율 에이전트가 **혼자 진행할 수 없게** 만드는 빈칸만 물어라. 한 번에 1~3개,
구체적으로. 판정 기준:

| 빈칸 | 자율성 깨나? | 행동 |
|---|---|---|
| 측정 가능한 완료 조건 없음 | **예** — 루프 못 빠져나옴 | 물어라 |
| 건드리면 안 되는 영역 불명확 | **예** — 범위 넘침 위험 | 물어라 |
| 비가역/외부발신 작업 포함 여부 | **예** — 가드 필요 | 물어라 |
| 사소한 스타일·네이밍 선택 | 아니오 | 합리적 기본값으로 채우고 명시 |
| Context 세부 (정황상 추론 가능) | 아니오 | 코드 읽어서 채워라 |

deep-interview 와의 선 긋기: 여기서 라운드가 3개를 넘어 늘어지면, 이건
deep-prompt 가 아니라 결정화가 필요한 신호다 — 사용자에게 `deep-interview` 를
권하고 멈춰라. 이 스킬은 *이미 대체로 명확한* 의도를 아티팩트로 굳히는 것이지,
모호함을 파고드는 게 아니다.

### 3. 고정 템플릿 채우기

아래 골격을 *정확히 이 섹션 순서로* 채운다. 모든 goal 프롬프트가 일곱 섹션을 다
쓰는 건 아니다 — Out of Scope 가 자명하면 뺄 수 있다 — 하지만 **Objective /
Success Criteria / Done & Report 세 개는 절대 빼지 마라**. 그게 자율성의 척추다.

```markdown
# Goal: <한 줄 제목>

## Objective
<달성할 것 한 문장. 동사로 시작. 모호한 형용사("개선", "정리") 금지 —
관찰 가능한 결과로.>

## Success Criteria
<에이전트가 스스로 체크해 루프를 끝낼 수 있는 조건. 각 항목은 검증 가능해야
한다 — 명령을 돌리거나 파일을 보거나 출력을 확인해 참/거짓이 갈려야 한다.>
- [ ] <검증 가능한 조건 1 — 예: `npm test` 가 0 exit>
- [ ] <검증 가능한 조건 2 — 예: `POST /login` 11번째 요청에 429 반환>

## Context
<레포, 관련 경로(file:line), 현재 상태, 환경. 에이전트가 맨바닥에서 시작한다고
가정하고 필요한 좌표를 준다. 추측 금지 — 읽고 확인한 것만.>

## Constraints
<사람 없이 도는 동안의 가드레일. 무엇을 건드리지 말지, 범위 경계,
비가역·외부발신 작업 정책.>
- <예: `src/legacy/` 는 읽기만, 수정 금지>
- <예: 커밋·푸시·PR 생성은 하지 말 것 — 변경만 두고 보고>

## Verification
<완료를 확인하는 정확한 명령·테스트. Success Criteria 와 1:1로 대응.
에이전트가 이걸 돌려 자가 판정한다.>

## Out of Scope
<명시적 비목표 — 범위 넘침 방지. 자명하면 생략 가능.>
- <예: 기존 테스트 리팩터링은 하지 않음>

## Done & Report
<끝났을 때 / 진짜로 막혔을 때 어떻게 신호하는가. 백그라운드 잡 완료 규약과
맞춘다: 완료 시 한 줄 결과, 막히면 무엇이 필요한지 명시, 구조적으로 불가능하면
이유.>
```

### 4. 검증 가능성 통과 — 약한 기준 거부

저장하기 전, **Success Criteria 의 모든 항목**을 통과시킨다:

- "에이전트가 사람한테 안 묻고 이걸 참/거짓으로 판정할 수 있나?" → 아니오면
  다시 써라. "잘 동작하면"·"적절히"·"깔끔하게"는 검증 불가 → 관찰 가능한
  조건으로 교체.
- 각 기준이 Verification 의 명령/관찰과 짝이 맞나? 짝 없는 기준은 에이전트가
  체크할 길이 없다.
- 좋은 예: `tests/auth/ 의 모든 테스트가 pass`, `429 가 11번째 요청에 반환`,
  `README 가 skills/ 의 모든 디렉토리를 링크`.
- 나쁜 예: `로그인이 더 안전해짐`, `코드가 더 읽기 쉬워짐`, `성능 개선`.

검증 가능성 사례·루브릭이 더 필요하면 `references/examples.md` 를 읽어라 (좋은
goal 프롬프트 2개 + 나쁜 것을 고친 before/after).

### 5. 저장 — 경로 확인 후 쓰기

`.md` 파일로 저장한다. 사용자가 경로를 줬으면 그대로. 안 줬으면 제안하고
쓰기 전에 확정받아라 (비가역까진 아니지만 위치는 사용자 결정):

- 레포에 `docs/` 컨벤션이 있으면 `docs/goals/<slug>.md` 제안.
- 없으면 `goal-prompts/<slug>.md` 또는 사용자 지정 위치.
- 파일명 `<slug>` 는 Objective 에서 kebab-case 로.

쓴 뒤 `/Users/carpdm/.codex/skills/claude-craft-core/references/output-contract.md` 의 종료 블록으로
보고한다 — `result:` 한 줄(무엇을 위한 goal 인지) + `프롬프트` 행의 상대경로와 `open`
명령(L1+L2). 그다음 그 내용을 goal 칸에 붙여넣어 백그라운드 잡으로 돌리면 된다고
안내하라. 예:

```
result: <topic> goal prompt 산출 — 검증 가능한 성공 기준 N개

산출물 — 열기:
- 프롬프트 `goal-prompts/<slug>.md`  →  `open goal-prompts/<slug>.md`

(`open` = macOS. Linux `xdg-open`, Windows `start`.)
```

## Anti-patterns

- **검증 불가 성공 기준** — "잘 되면 끝"은 자율 에이전트에게 무한 루프 또는
  조기 종료를 뜻한다. 모든 기준은 명령/관찰로 판정 가능해야 한다. 이게 이
  스킬의 존재 이유다.
- **deep-interview 흉내** — 모호함을 파고들겠다고 라운드를 끝없이 늘리기. 3라운드
  넘으면 멈추고 deep-interview 로 보내라.
- **가드레일 누락** — 비가역·외부발신 작업(push, 배포, 삭제, 메일)을 Constraints
  에 안 박으면 사람 없는 동안 사고가 난다. 의심되면 "변경만 두고 보고"로 막아라.
- **Context 추측** — 읽지 않은 경로·함수를 단언. 에이전트는 그 좌표를 믿고
  움직인다 — 틀리면 처음부터 헛돈다. Read/Grep 으로 확인한 것만 써라.
- **Objective 에 형용사** — "개선/정리/최적화"만 적으면 무엇이 완료인지 비어
  있다. 관찰 가능한 결과 동사로.
